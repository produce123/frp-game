## 2. 规则要点（原项目花真实 bug 换来的，别顺手"优化"掉）

| 规则 | 细节 |
| --- | --- |
| 弹药 | 每轮总弹数 `随机[人数×2, 人数×3]`，实弹数 `随机[1, 总数-1]`（保证实空都有）。**两种各剩多少公开，先后顺序保密** |
| 装填 | 弹匣打空立刻自动换弹，新一轮从**最小座号的存活玩家**开始（该玩家戴着手铐也要跳过） |
| 发牌 | 手牌 4 张→摸 0；3 张→摸 1；其余→摸 2；**全局第一回合最多摸 1** |
| 空弹打自己 | 不掉血、**保留回合**，可以继续操作 |
| 实弹打自己 | 掉血且回合结束 |
| 手锯 | 下一发实弹伤害 2；打出空弹也算浪费；**已经锯过时不允许再锯（防浪费）** |
| 放大镜 | 情报只有本人可见（`state.knowledge[自己]`），换一发子弹即作废 |
| 逆转器 | 反转当前这一发；**是公开信息**（原本知道的人可以顺推新值）。⚠️ 但**公开的「实弹 N / 空弹 M」统计一个字都不许变** —— 变了就等于白送一次放大镜（用户实机报过：手里没有放大镜，用了逆转器却看见数字从 5/3 变 6/2，等于告诉他这一发是实弹）。所以统计数的是 `magazine.faces`（**装填时那一面**），见 §2.1 |
| 啤酒 | 退出当前这一发，**退出来的类型公开** |
| 香烟 | 回 1 血，上限 5；满血使用允许但浪费 |
| 手铐 | 封锁对手**下一回合**；不能铐自己，也不能铐已被铐住的人 |
| 手铐的跳过 | 被跳过者的手铐在"被跳过的那一刻"消耗掉。**交接回合时如果其他人都被锁住，回合必须回到原玩家身上**，不能顺延给刚被跳过的人（那等于白送一个回合） |
| 肾上腺素 | 随机偷一张并**立刻使用**；**不能偷肾上腺素本身**（防无限递归）；偷到手铐要二次指定目标；**没有合法目标时这张牌直接作废，不许挂起**（会死锁） |
| 牌堆 | 7 种 × 4 张 = **28 张守恒**（手牌 + 摸牌堆 + 弃牌堆 + "飞行中"的那张）；摸牌堆不足 4 张时回收弃牌堆，洗匀后放到摸牌堆**底下**（顶部 = 数组头） |
| 防泄露 | `viewFor` 是唯一出口。弹匣真实顺序、他人手牌内容、他人放大镜情报**绝不能出现在任何报文里**。**每一步的状态补丁（`entry.s`）走同一条口径**（见 §4.9.1） |

**不变量检查**（`checkInvariants`）里有一条最关键：
"当前玩家必须永远有棋可走" —— 打破它就是死锁，`sim.mjs` 每一步之后都会查。

### 2.1 公开的弹药统计按**装填时那一面**记账（`magazine.faces`）

用户实机报的漏洞（2026-10）：

> "转换器功能有漏洞，我没有放大镜、不知道这一发子弹的真实情况，但我用了转换器后，
>  却可以看到上方子弹统计从'实弹 5 空弹 3'变成了'实弹 6 空弹 2'，
>  这间接告诉了我这一发子弹现在是实弹。"

根因很直白：`remainingCounts()` 原来数的是**枪膛里此刻那一面**（`magazine.shells`），
而逆转器翻的正是那一面 —— 数字一动就等于白送一次放大镜。

**现在的口径**：`state.magazine.faces` = **装填时每一发的那一面**，
`reloadMagazine()` 写一次，之后**只读**（逆转器只翻 `shells`）。公开统计数 `faces`：

| 时刻 | 统计说的是什么 |
| --- | --- |
| 装填后 | 各有多少发 —— 与真实剩余完全一致 |
| 用了逆转器、那一发还在膛里 | **一个字都不变**（"这一轮装填时的账"） |
| 那一发打掉 / 退掉之后 | 立刻又等于真实剩余（差的那发已经不在枪里了） |

三条硬不变量（`rules.test.mjs` 的「逆转器」两条用例钉着）：

1. **总数永远等于"枪膛里还剩几发"**（谁也不多、谁也不少）；
2. 同一时刻**最多只有膛里那一发被翻过**，所以除了它，统计与真实剩余**逐发一致**；
3. 膛里那一发离开枪膛之后，统计**立刻**等于真实剩余。

⚠️ **代价（如实说）**：膛里那一发被翻过时，公开统计会与枪膛里那一发**故意不一致**
（比如统计说"还剩 1 实弹"，而膛里实际已被翻成空弹）。这是**刻意的**：
宁可让统计慢一拍，也不能让逆转器变成免费放大镜。

⛔ **别改回 `shells[i]`**：改回去单机、AI、规则单测看着全都正常（那是**联机实机**才看得出来的漏洞）；
`tests/rules.test.mjs` 的 `setMagazine()` 辅助函数也必须同时写 `faces`
（少写它 = 单测里逆转器又变回放大镜，而线上代码其实是对的）。
`cloneState()` 也要带上 `faces`（它做的是深拷贝，漏了字段就会在"先试后回滚"的测试里漂移）。

## 3. 分层铁律（违反任何一条都会以奇怪的方式坏掉）

### 3.1 `js/engine/**` 与 `js/ai/**` 里不许出现 `document` / `window`

这两个目录会被 `server/games/shell-gambit.mjs` 在 Node 里 import
（服务器是权威，见 `DECISIONS.md` D2）。写了 `document` 就**只有等浏览器玩到那一步才发现**，
Node 侧测试全绿 —— 因为它根本没执行到那一行。

> **改成那样会怎样坏**：在 `engine.js` 里加一句 `document.querySelector(...)`，
> 服务器开局就会 `ReferenceError: document is not defined`，
> 表现为"点开始游戏没反应/报开局失败"，而所有 Node 测试仍然全过。

**连注释里都不要写这两个词**（会被 grep 命中）：`engine.js` 顶部注释里的表述是
"**绝不能出现任何浏览器宿主 API**"—— 不点名，点名的字面量自己就会把那条 grep 打脏。

### 3.2 界面只能吃 `viewFor` 裁剪过的视图

`board.js` / `match.js` / `app.js` 拿到的都是视图，**不是**引擎的 `state`。
单机也一样 —— 单机没有作弊风险，但**必须走同一条路**，否则"联机路径"永远是没测过的代码。
按钮列表整个由 `view.me.legal` 决定，界面**不自己判断合法性**。

> **改成那样会怎样坏**：让界面直接读 `state.magazine.shells` 显示"下一发是实弹"，
> 单机看着挺好，联机时服务器根本不会把 `shells` 发给你 —— 界面要么显示 `undefined`，
> 要么（更糟）你为了让它能显示而在 `viewFor` 里放出 `shells`，那整局游戏就明牌了。

⚠️ **日志里"每一步的状态补丁"（`entry.s`）是同一个出口的第二份数据**（逐步同步用的，
见 §4.9.1）：引擎先按人存成表，**出报文前**由 `narrowLogEntry()` 裁成"我自己那一份"。
裁剪口径必须与 `viewFor` 完全一样 —— 少裁一张表，界面就能看到对手手牌，
而**单机看着一切正常**。`tests/rules.test.mjs` 的「补丁不泄露」用例逐字段钉着这件事。

### 3.3 服务器侧的 AI 必须**同步**在 `act()` 里跑完

`server/rooms.mjs` **没有**"稍后再推一次状态"的机制。所以
`server/games/shell-gambit.mjs` 的 `act()` 里，真人走完之后用一个
`while` 循环把所有 AI 回合一次跑完（`MAX_AI_STEPS` 是防御性上限）。

> **改成那样会怎样坏**：用 `setTimeout` 让 AI "想 1 秒再动"，
> 那一刻 `broadcastState` 早就把"轮到 AI"的视图推出去了，
> 之后**再也不会推第二次** —— 真人屏幕上永远停在"等待对手行动"，谁也没报错。

浏览器里的**单机**对局是另一回事：那边没有服务器，用 `setTimeout` 加 950ms 的
"AI 思考感"是对的（`js/ui/match.js`）。**单机的 AI 延迟不能照抄到服务器。**

### 3.4 不在游戏里问玩家名字

身份来自账号（D5）：`GameNet.me`（WebSocket 的 `ready`），页面一打开先用
`/api/me` 顶一下。整个游戏页**只有房间号一个文字输入框**（那是 `FrpRoom` 画的）。

## 4. 还要注意的几处（都是这次真撞过的）

### 4.1 游戏页必须自己调 `GameNet.connect()`

`shared/net/net.js` 只**定义**连接能力，不会自己连。平台外壳调的是
`web/assets/js/app.js` 里的 `Net.connect()`，**游戏页必须自己调一次**
（`blade-steed` 也是在它的 `app.js` 里调的）。

> **改成那样会怎样坏**（本次真撞了，而且骗了很久）：漏掉 `connect()` 之后
> · 名字和 ID **照样显示**（那是 `/api/me` 给的，不走 WebSocket）
> · 单机人机对局**照样能玩**（纯本地）
> · 只有点【创建房间】时哑掉 —— `GameNet.send()` 发现 socket 不是 open 就直接
>   `return false`，什么都不发，界面干等在"创建房间"那一屏，**一个报错都没有**。
>
> 所以 `js/ui/app.js` 的 `init()` 里 `net.connect()` 放在最前面，
> 并且 `browser.e2e.mjs` 专门等一次 `GameNet.connected === true` 才往下走。

> ✅ **平台侧已经修掉了**（captain 在三个游戏都搬完之后统一收口）：
> `shared/ui/room.js` 的 `FrpRoom.mount()` 现在会代劳一次
> `if (!Net.connected) Net.connect()`。所以游戏自己再调一次是**双保险**，留着无害。
> 另外 `tools/check-game.mjs --browser` 现在也硬性要求
> "真的连上 + 点【创建房间】真的拿到 6 位房号"，漏了 `connect()` 会被机械体检当场抓住。

### 4.2 座位是随机的，开局可能直接轮到 AI

单机对局创建完必须调 `match.start()` 主动推一把 AI。

> **改成那样会怎样坏**：不推的话，一半的开局（AI 先手那一半）界面直接干等，
> 看起来像"AI 卡住了"，实际是**没有任何人去驱动它**。这是浏览器测试撞出来的。

### 4.3 人机是**房间的座位**（`meta.minSeats` / `players[].isBot`）

**平台契约：人机由房间层造座位，游戏只认标记。** 实现在两处，各管一段：

| 谁 | 干什么 |
| --- | --- |
| `shared/ui/room.js` + `server/rooms.mjs`（**不要改**） | 房主按「＋ 添加人机」→ 多一个成员（`{ id:'bot:1', name:'虎', isBot:true }`，名字**单字**、从 `meta.botNames` 里挑）；`start()` 把**真人 + 人机一起**放进 `players` 交给 `createMatch`；座位数不够 `meta.minSeats` 时它自己就拦住（「开始游戏」灰着） |
| `server/games/shell-gambit.mjs` | 只把 `players` 里 **`isBot === true`** 的座位映射成 AI 座位（`isAi: true` 进引擎）；座位数 <2 或 >4 就 `throw`（防御性第二道闸） |

**`meta` 现在是这四个数**：

- `minPlayers: 1` —— 房间层数的是**真人**下限，"至少 1 个真人"。
- `minSeats: 2` —— **总座位**下限（人机也算），= 引擎的座位下限。
  平台有两处吃它：`room.js` 决定「开始游戏」灰不灰，`tools/check-game.mjs`
  拿几个座位调 `createMatch`。**写错这两处都会坏**。
- `maxPlayers: 4`、`allowMidJoin: false`。
- `botNames` —— **直接 `import` 单机那套池子**（`js/ai/ai.js` 的 `AI_NAME_POOL`，
  虎狼鹰豹蛇狐枭鲨鲸隼）。⚠️ **不许在服务端抄一份字面量**：抄了以后单机改字表、
  人机名字不跟着变，两边就会各自演化。`tests/rules.test.mjs` 用
  `assert.equal(meta.botNames, AI_NAME_POOL)` 钉住"同一个数组"。

**五条硬规矩（都是实测出来的，别改坏）**：

1. **AI 由服务端同步驱动，不许用定时器**（见 §3.3）。`createMatch` 建完局、
   `act()` 里真人走完，都要 `runAi()` 一直推到"该真人了"为止 ——
   只要返回时回合还在 AI 身上，客户端就永远停在"等待对手行动"。
2. **座位表原样交给引擎**：传几个座位就是几个，**不截断、不兜底、不多造**。
   老口径那套"真人优先、不够就裁 AI"作废了 —— 现在房间层在开局前就管着座位，
   游戏层多造一个座位反而会和成员列表对不上。
3. **身份标记要进视图，但名字叫 `isAI`**：`js/view.js` 的 `viewFor()` 把座位上的
   `isAi` 注入成 `players[].isAI`（**公开身份**，成员列表里本来就写着「人机」）。
   界面靠它画灰圆环（见 §4.11）。**不许按名字猜**：人机和真人用的是同一张字表。
4. **房间层的字段名不进视图**：座位条目字段**恰好**等于 `PUBLIC_PLAYER_FIELDS`
   （含 `isAI`）；`isBot` / `isAi` 都不许漏进去。
   `tests/ai-fill.test.mjs` 有一条逐字段的哨兵用例盯着。
5. **客人（非房主）看到的是一行只读文字**（"人机由房主添加"）。
   `js/ui/app.js` 的 `mount()` 里**没有** `options`、也**没有** `renderSetup` ——
   本作在准备区一个设置项都没有（见 §4.4）。

**人机的名字是单字**（「虎」「狼」…，来自 `meta.botNames`），id 是 `bot:N`
（玩家 ID 的字母表里没有冒号，撞不上真人）。单机【人机对局】用的是另一套 id（`ai:N`）
和同一个字表 —— 两处 id 命名不同是刻意保留的，别去"统一"。

> ⚠️ **本节原来写的是"`meta.minPlayers` 是 1，房主一个人也能开局（靠电脑补位）"，
> 那套说法已经作废**（2026-02 那一版改的）。老口径下：
> `createMatch` 按 `options.aiFill` 造「电脑1」「电脑2」，缺省兜底补 1 个，
> 房主明确选 0 时抛"只有你一个人开不了局：把「电脑补位」打开…"，界面里
> `renderSetup` 画一个"补几个电脑"的 0/1/2/3 选择器。
>
> **为什么作废**：那套东西把"房间里有几个座位"这件事**分散到两个地方**记
> （房间层的成员列表、游戏自己的 options），两边一旦不一致界面就开始撒谎
> （界面写着"补 3 个"、房里却只有 1 个人机座位）。
> 现在平台外壳统一管座位（加/移除/占位/名字），游戏只管"哪些座位是电脑"——
> 这就是用户点名要的新契约。
>
> **作废的后果（改回去会怎样坏）**：
> · 界面里那个"补几个电脑"和服务端的座位表对不上 —— 玩家点了没反应或者数字骗人；
> · `meta.minSeats` 这条通路没人用，「开始游戏」在一个人时又变成"点了被拒"；
> · 三个人机名字「电脑1」会同时出现在**房间成员列表**和**牌桌座位**上却互不相干。
> 老的四条规矩（clampInt 收口 / 缺省兜底 / 明确 0 拒绝 / 名字「电脑1」）**全部作废**，
> 对应的用例已经按新契约重写。

### 4.4 座位数超范围一律 `throw`；`options` 里没有任何游戏设置

```js
createMatch(players, options)
// 座位 < 2  → throw('至少要 2 个座位才能开局（人机也算座位）')
// 座位 > 4  → throw('最多 4 个座位（现在 N 个）')
```

- **房间层不该这么调**：它在 `players.length < minSeats` 时就先拦住了，
  给房主弹的是"座位不够：至少要 2 个座位（现在 1 个）。按「添加人机」补一个，或者等朋友进来"。
  游戏层这两条 `throw` 是**防御性第二道闸** —— 真被这样调进来时（比如有人从控制台发消息），
  抛出来的话要能直接读懂，而不是引擎那句通用的"需要 2–4 名玩家"。
- **`options` 一个字段都不读**（文件里明写 `void options;`）：房主设置只存在他自己页面里，
  随 `room.start` 一次性发出去；本作现在**没有任何**游戏设置项。
  垃圾 `options`（`null` / `'abc'` / `{ aiFill: 3 }`）**不许改变座位表**，
  `tests/rules.test.mjs` 与 `ai-fill.test.mjs` 各有一条用例逐个钉住。

> ⚠️ **本节原来讲的是 `options.aiFill` 的 `clampInt` 收口（越界/小数/字符串收口到
> 0..maxPlayers-真人）、以及"收口成 0 走兜底、恰好是数字 0 才是拒绝"那一整套区分 ——
> 全部作废**，`clampInt` 已经从服务端删掉了。别再照那段改回去。

### 4.5 真人掉线 → 座位由 AI 接管

`removePlayer` 不返回 `false`，而是把那个座位换成 AI 继续打完。

> **为什么这么做**：本作是回合制、状态全在服务端。掉线就判负的话，
> 剩下的人手里的牌、已经公开的弹药数全都会变成一局死棋。
> 让 AI 接管至少"这一局能打完"。**这是有意偏离原项目的**，原项目是房主直接判出局。

⚠️ **接管时刻意不翻座位上的身份标记**（不掉线的那位真人，视图里 `isAI` 仍然是 `false`）。
理由：`isAI` 回答的是"**这个座位是不是房间里的人机**"，而接管回答的是
"**谁在替这个座位打**"。房间成员列表里这个人照样是「掉线中」的真人 ——
两处必须一致，否则同一个人会同时显示成"掉线中的真人"和"人机"，圆环颜色也会乱跳。
`ai-fill.test.mjs` 有一条用例钉着这个"不翻"的行为。

### 4.6 平台组件的高度要用 CSS 变量/覆盖，不要改 `shared/`

`css/style.css` 末尾那一节只做两件事：覆盖 `--ui-*` 变量让平台组件长成本作的样子、
把几个低于 44px 的按钮顶上去（`.ghost-btn` 42px、`.icon-btn.tiny` 34px、
对局记录展开条 30px、房间号按钮 44px 在窄屏换算下来是 43.xx）。

> **改成那样会怎样坏**：直接改 `shared/ui/ui.css` 会让另外两个游戏一起变，
> 而且那是别人的文件（`docs/GAME-SPEC.md` 明确要求"各游戏只改自己的 CSS"）。
> 另外注意本作的窄屏媒体查询阈值是 **400px**（原本 380px）：
> 380 时 360px 视口下按钮会掉到 43.xxpx，实测**过不了 ≥44px** 那条硬指标。

### 4.7 浏览器自动化点击会"点空"（两种不同的点空）

**第一种：目标被重画掉了。** `page.click()` 发的是 `mousePressed` + `mouseReleased`
**两个**真实事件。点平台设置项时 `FrpRoom.setOption()` 会**立刻重画整块等待区**，
释放时目标已经被摘出 DOM —— 这一下就点空了，而且**毫无报错**。

**第二种：被平台提示条吃掉。** `.frp-toast` 在 `shared/ui/ui.css` 里是
`position:fixed; bottom:18px` 且 `pointer-events:auto`，而 `page.click` 会先
`scrollIntoView({block:'center'})` 再按**屏幕坐标**点 —— 牌桌矮的时候
"对自己开枪"正好落在右下角，那一下点在了提示条上。
实测症状：click 事件的目标是 `.frp-toast`，按钮完全收不到，**没有任何报错**。

`tests/browser.e2e.mjs` 的对策：会重画的按钮一律用页面内 `el.click()`；
发真实鼠标事件之前先把 `.frp-toast.is-visible` 点掉。

⚠️ **顺手记一条 2026-10 的决定：本作在对局中不再往提示条里弹任何东西。**
用户第三条实机反馈是"放大镜：下一发是实弹 / 虎 被带上铐 这种提示弹窗挡住我的操作按钮" ——
那两条正是 `board.js` 里**自动**触发的 `onInfo()`（放大镜情报、戴手铐提示），
它们落在右下角固定位置的 `.frp-toast` 上，正好压在动作按钮上。
现在这两条**连同只为它们存在的 `knows`/`snap` 管线一起删掉了**，播报本来就在「对局记录」里。

- **还留着 `onInfo()` 的只有"用户自己点出来"的那几处**：选目标时那句提示、
  ☰ 菜单里的音效/特效开关反馈。**判断标准是"是不是我主动点的"**，不是"重要不重要"。
- **放大镜情报没有丢**：牌桌上有一颗常驻的 HUD 小牌（`renderKnowledgeChip()`），
  写着「已知下一发」，它**不在**底部提示条里、也不挡按钮。
- ⛔ **别再往这里加自动提示**：`.frp-toast` 是**平台共用**的固定定位浮层
  （`shared/ui/ui.css` 的 `bottom:18px` + `pointer-events:auto`），
  这个布局是三个游戏共用的，本作改不了也不该改（§4.6）。要提示就往「对局记录」里写。

### 4.8 座位不够时「开始游戏」是**灰的**（`minPlayers: 1` + `minSeats: 2`）

两个数管两件事，别混：

| 数 | 谁读它 | 含义 |
| --- | --- | --- |
| `meta.minPlayers = 1` | `server/rooms.mjs` 的 `start()`；`app.js` 传给 `mount()` 的 `minPlayers` | **真人**下限。写 1 才对：一个人建房是正常玩法（补个人机就能开） |
| `meta.minSeats = 2` | `shared/ui/room.js`（随 `room.state` 下来）+ `tools/check-game.mjs` | **总座位**下限（人机也算）。座位数 < 它 →「开始游戏」**禁用** + 一句"至少要 2 个座位…按「添加人机」补一个" |

所以一个人刚建好房时：**按钮是灰的**（座位 1 / 2），旁边写着怎么补座位 ——
点不动是**对的**，不是 bug。按一下「＋ 添加人机」按钮立刻解禁。

平台侧那道闸仍然在：`server/rooms.mjs` 的 `start()` 只认座位数，
`players.length < minSeats` 就拒绝并推一条提示条。`browser.e2e.mjs` 里
**绕过灰按钮直接发一条 `room.start`** 去验这条链路（点按钮已经点不动了，
只有从控制台发消息才摸得到）—— 那条用例就是"最后一道防线"的证明。

> ⚠️ **本节原来写的是"单人建房时『开始游戏』必须是**可点**的（`minPlayers: 1`）"，
> 那半句已经作废**：`minPlayers: 1` 仍然是对的，但**决定按钮灰不灰的已经不是它了**
> —— `room.js` 现在先看 `minSeats`（`seats < minSeats` 就禁用），
> 只有老版本（没有 `minSeats` 字段）才回退到 `cfg.minPlayers`。
> 所以"想让一个人点得动开始按钮"的正确做法是**加人机座位**，不是把 `minSeats` 写小：
> 写小了 `createMatch` 会抛"至少要 2 个座位"，玩家看到的就是"点了报开局失败"。

### 4.9 逐条演出：`FrpAnim.push()`，每步 450–700ms（用户需求 1）

`board.js` 的 `playNewEvents()` 原来是**同步 for 循环**一次性把新事件全播完 ——
服务端一次推来 5 条事件（我开枪 + 对手开枪 + 出局 + 交接回合 + 换弹），
玩家在**同一帧**里看到全部结果，等于没有演出。

现在改成交给平台的串行队列：

```js
FrpAnim().push(steps, (e) => playStep(e));   // 每步返回它占多少毫秒
```

- **顺序、数量、去重一个字不许变**：`steps` 还是"`log` 里 `n > lastEventN` 的那些，
  按 `n` 升序"，`lastEventN` 照样推进到最后一条的 `n`。改的只有**时间轴**。
- **每步 450–700ms**（`eventMs()`：实弹命中 700 / 空弹 560 / 出局 650 / 用道具 560 /
  跳过 520 / 新一轮 520 / 回收 480 / 交接回合 450 / 结束 480）。分量重的长一点。
- **不许做"跳过/快进"**：用户明确要求逐条看完。队列本身也没有 skip 接口
  （`shared/ui/anim.js` 里只有 `setEnabled/pace`）。
- **演出期间画面不是"立刻跳到结果"**（这一行 2026-02 改写，老口径作废）：
  演到第几步，画面就是第几步 —— 见下面 §4.9.1「逐步同步」。演出期间唯一"已经跑到前面"
  的是**按钮的合法性**（服务端那一帧早就把回合推进过了），所以输入仍然锁着，见 §4.10。
  ⚠️ 老版本这一段写的是"`render(view)` 照旧立刻把最新一帧画出来（所以按钮/血量/弹药数都是新的，
  只有'播报'在排队）"——**那句话描述的正是用户报的那个 bug 本身**：
  "ui 动画还没播放完对方的血量就已经是结算状态了"。别照那句改回去。
- **单机那 950ms 不许动**：`js/ui/match.js` 的"电脑思考感"是本地对局的调性
  （见 §3.3），和这里的逐条演出是两回事。

⚠️ **异步带来的一个新风险，已经踩过**：一步可能排在 700ms 之后 ——
那时候玩家可能已经点了「离开对局」（`dispose()` 把宿主 `innerHTML` 清空），
或者已经开了新的一局（`mountBoardFor()` 先 dispose 再重建）。
所以牌桌里有个 `disposed` 旗子：`dispose()` 时置位，`playStep()` 一开头就看它，
**已卸的牌桌剩下的步立刻作废**（返回 0，队列快速排空）。
没这一条时真浏览器里会刷屏
`[FrpAnim] 播放一步时出错 TypeError: Cannot read properties of null (reading 'classList')`
（`feedAdd()` 往一个已经被清空的宿主里写 DOM）——**这是 `browser.e2e.mjs` 抓到的**，
Node 侧测试完全看不见。

`browser.e2e.mjs` 里那条"逐条演出"用例（4c-A2）的观测方法是：
断言"对局记录条数"**分多次**长起来、相邻两次间隔 ≥300ms（采样 50ms 一次，
**和点击在同一次页面求值里**，见下面 §4.9.1 的 4c-D）。
同步老写法下只有 1 次增长，立刻红。实测一次回包**分 4 次**长起来
（时刻 51/577/1074/1581ms，间隔 526/497/507ms —— 每次跑都不完全一样）。

⚠️ **这一段必须紧跟"我这手"那一次点击**（用例里 4c-A 点完立刻采样）。
实测教训：开局第一手 `room.act` 的回包是**最富**的一帧（我这一手 + 人机的整个回合），
而**第二手**的回包可能只多带去 1 条"对局记录" —— 那时队列照样老老实实演了 2.2 秒
（采样轨迹里 `busy` 一直为真、`n` 却不动），"分多次长起来"这条会因为**没内容可长**
而假红。所以：**把观测塞在第一次点击后面**，别接在第二次点击后面。

#### 4.9.1 逐步同步：整块牌桌按步走（用户需求 4，D14）

**症状**（用户原话）："恶魔轮盘在线对局中，ui 动画还没播放完对方的血量就已经是结算状态了，
血量等参数与动画不同步"。

**根因**：老的 `render(nextView)` 一收到报文就按**最终**状态把整块牌桌重画一遍，
只有"播报 + 特效"进了 `FrpAnim` 队列 —— 演出还要演 2.7 秒，画面早就是结算后的样子了。

**现在的做法**（`board.js`）：牌桌手里有**两份**视图

| 视图 | 是什么 | 谁用 |
| --- | --- | --- |
| `authView` | **权威视图**（服务器最新那一份） | 只在对账时用 |
| `view` | **显示视图** = 权威视图 + 已经演到的那些补丁 | `paint()` 照着它画整块牌桌 |

```js
// 每一步：贴补丁 → 重画整块牌桌 → 演这一步的特效/音效 → 返回该步毫秒数
function playStep(e) {
  if (disposed || !view) return 0;   // 牌桌已卸，剩下的步立刻作废（见上一节）
  applyStepPatch(e);                 // 把 entry.s 贴到**显示视图**（浅拷贝，⛔ 别动权威对象）
  paint(view);                       // 回合数/弹药数/锯子/血量点/手牌/动作区全跟着走
  handleEvent(e);                    // 播报文字 + 特效 + 音效
  return eventMs(e);
}
```

- 演完最后一步、**队列真的空了**之后，用权威视图整体**对账**一次（兜住补丁没覆盖到的字段）。
- ⚠️ **对账不许插队**：队列还在演的时候又来了新视图，只把它记成新的权威视图、把新事件接到队尾，
  半路绝不重画 —— 否则就是"演到一半突然跳到结果"。对账是 60ms 一次的小轮询，只在有账要收时活着。
- **兜底**：某条没有补丁（老报文/补丁缺失）→ 照旧演特效但**不改数字**，最后由对账收口；
  整帧一条 `s` 都没有 → 走改动前的行为（立刻画最终状态 + 特效逐条演）。
  ⚠️ 一条贴不上、**后面几条也就都别贴**（补丁是差量，链断了硬叠就是错数），
  所以 `applyStepPatch()` 会检查 `e.n === view.seq + 1`，对不上就整帧交给对账。
- ⛔ **不许让客户端"照事件自己算"**（那是在界面里重写一遍规则，违反铁律三）：
  血量 / 弹药 / 手牌 / 回合全部来自服务器给的补丁，界面只负责贴。

**红线：补丁里绝不放什么** —— 与 `viewFor` **同一套裁剪口径**，别自己另开一套：

| 绝不放 | 为什么 |
| --- | --- |
| `magazine.shells`（弹匣真实顺序） | 放出去整局明牌。公开的只有 `magazine.{live,blank,total}` |
| 别人的手牌内容 | 补丁里只能有**我自己那一份**：`hands` 表的 `hands[我]` → 单数 `hand`，表整个删掉 |
| 别人的放大镜情报 | 同上（`knows` 表 → 单数 `knows`） |
| `seed` / `drawPile` / `discard` / `rng` | 种子 + 牌堆顺序等于明牌 |

实现分两半：**引擎**（`engine.js` 的 `publicSnapshot()` / `diffPatch()` / `pushEvent()`）
生成补丁，私有信息**按人存成三张表**（`hands` / `legals` / `knows`）；
**出报文之前**由 `narrowLogEntry()` 按 viewer 把表裁成单数。
`js/view.js` 里的 `PUBLIC_PATCH_FIELDS` / `PRIVATE_PATCH_FIELDS` / `PATCH_PLAYER_FIELDS`
就是"补丁里允许出现什么"的清单（测试拿它逐字段核对）。

⚠️ **踩过一次的坑**：那三张表里有一对**表名和单数名同名**（`knows` → `knows`）——
**必须先删表、再提单数**。顺序反了，`delete out.knows` 会把刚提上来的那份情报一起删掉，
表现是"逐步演出时「已知下一发」提示条要等最后对账才冒出来"，
而单机看着一切正常（单机对账来得快）。这个 bug 是 `tests/rules.test.mjs` 新加的那条
「补丁不泄露」用例抓到的。

**首次挂载 / 换局：默认一条旧条目都不回放 —— 但"开局就在日志窗口里"时例外，要回放**：

- 默认**只画权威视图、不回放**（`takeFreshEvents()` 返回 `reset` 或 `view` 还没有时）：
  刚挂上牌桌（打了一半才进来 / 重连恢复座位 / 从平台好友卡片进来）时，拿到的是**当前**状态，
  而日志窗口里还挂着几十条旧条目、游标却是 0。把这些旧条目一条条排队演，一是莫名其妙演很久，
  二是把补丁叠在最终状态上 → **血量点 / 弹药数会算出错的数**（补丁只说"谁变了"，不说"原来是多少"）。
  "再来一局"之后 `seq` 从 0 重来，旧游标比新序号还大，同理。
  这条路必须**强制**重画（`reconcile(true)`）：换局后权威 `seq` 比显示 `seq` **小**，
  那句"显示视图已经追平就不用画了"会把上一局的画面留在屏幕上。
  游标同时对齐到窗口最后一条的 `n`（相当于"这些你已经看过了"）。

- ⚠️ **例外：`openingSteps()` 认得出"基线"时，从第一步开始演**（2026-10 加的，
  修的是用户实机反馈 **"我明明在 3 号位，却是第一个行动"**）。
  判据只有一条：**日志的第一条就是这一局的第一步（`n === 1`）而且带着补丁** ——
  那一条的补丁是**全量快照**（`pushEvent` 的 `patchBase` 是按 state 对象存的 WeakMap，
  一局的第一条取不到基线，天然全量；`tests/rules.test.mjs` 的「开局基线」用例逐字段钉着它）。
  有基线，差量就叠得上去，于是可以一条条把开头演出来：`第 1 轮 → 1 号位摸牌 →
  1 号位开枪 → … → 轮到我`，玩家这才看得见"1 号位先行动"。

  **为什么非修不可**：`server/games/shell-gambit.mjs` 的 `createMatch`/`act()` 会把
  人机的整个回合**在广播之前**同步跑完（§3.3：房间层没有"稍后再推一次"的机制），
  所以那几步全都发生在玩家拿到第一帧**之前**。老写法一条都不回放 ——
  玩家一进对局就已经轮到自己，看起来就像"3 号位先手"。**座位和回合一直是对的，
  是开场那几步根本没演给人看。**
  ⛔ 所以这条**不许**用"把房主放到 1 号位"去糊（座位故意是随机的，见 §4.2）。

  **实现**（`board.js` 的 `playOpening()`）：先把第一条补丁（全量）贴到权威视图的拷贝上
  当地板，**再把 `view.seq` 退回 0**，然后照常 `queueSteps(整段日志)` ——
  第一条的 `n === 1` 正好接得上链子（`applyStepPatch` 只认 `n === seq + 1`），
  它的内容已经在地板里了，再贴一遍是**幂等**的。演完照常对账。

  **代价**：单机对局挂上牌桌时也会演一遍"第 1 轮 + 摸牌"（同一份代码，一行都没分叉），
  玩家第一次能出手会晚约 1 秒 —— 和"卡一点就卡一点没事的"同一条口径（D10）；
  用例里每个真点击之前本来就 `waitIdle()`。**打了一半才进来 / 重连那条路没变**
  （第一条不是 `n === 1`、没有基线 → 照旧只画结果）。

  **实测防线**：`browser.e2e.mjs` 的 `assertOpeningReplayed()` ——
  单机与"1 真人 + 1 个人机座位"两处都断言**对局记录的第一条是「第 1 轮」**。
  老写法下这一条**永远不会出现**（它只在真的又开一轮时才播），所以这条会当场红。

**新用例：`browser.e2e.mjs` 的 4c-D（真浏览器，唯一硬证据）**

把"点击 + 同一帧取值 + 整段演出的采样"合成**一次页面求值**（分开求值会有 CDP 往返插在中间，
2~3 秒的窗口根本抓不稳，断言会偶发红）。采样每 50ms 记一次
`{busy, dataset.seq, 实弹/空弹/回合数/锯子, 每个座位的血量点/存活/是否轮到它}`；
然后拿采样里的 `dataset.seq` 去 `room.view.log` 找**同一条**日志的补丁 `s`，
断言"补丁说多少、屏幕上就是多少"，**并且至少采到一次明显不是最终结算值的样本**；
队列排空 + 对账落地之后再断言整块牌桌**等于权威视图**。实测（本机）：

```
逐条演出：对局记录分 4 次长起来（时刻 51/577/1074/1581ms，间隔 526/497/507ms，最终 4 条）
逐步同步：采样 38 次，其中 27 次停在演出中途（第 3/4/5 步 < 最终第 6 步），
        18 次明显不是最终结算值；每一步的弹药数/血量点/回合数/轮到谁都与那一步的补丁一致
对账（队列排空后）：第 6 步 = 权威视图，实弹 2 / 空弹 1 / 第 1 回合，血量 TYYUM85:5 bot:1:5
```

（每次跑的数字都不一样：`38/27/18` 随这一帧打了几枪、采样落在哪一步而变。
断言的是"有中途样本 + 每一步都对得上 + 至少一次不是最终值"，不是这些具体数字。）

**单机也要按步走**（同一个 `render()`）。`browser.e2e.mjs` 的单机那一段把
`FrpAnim.push` 包了一层，看在队列里排了什么，实测：

```
单机逐条演出：这一手排进队列 2 步（序号 3/4），每一步都带"这一步的状态补丁"；
点完那一瞬画面停在第 3 步（不是最终第 4 步）
```

（单机是**同步**回结果的 —— 点 → 本地引擎跑完 → `onUpdate` → `render` —— 所以
"点完那一瞬"就能断言画面停在第 1 步。⚠️ 单机一帧常常只有 1~2 步（AI 是 950ms 一步单独推的），
步数不足 2 时"画面还不是最终值"这条无从谈起，用例会跳过；**画面中途 == 那一步**的
硬证据在联机的 4c-D。）

### 4.10 不做本地预演 + 演出期间锁输入（用户需求 2，D10）

**这一节整段重写过**：老版本叫"我自己的动作**立刻演**"（乐观起手），
被用户实测否掉了。照现在的口径做，**别改回去**；完整理由与被否掉的选项见
`docs/DECISIONS.md` D10，`docs/GAME-SPEC.md` 第 12 节的禁止清单里也写着这两条。

#### ① 点下去到服务器回包之间：本机不播任何动画、不出任何音效

`doAction()` 现在只剩"把意图交出去"：

```js
function doAction(action) {
  if (animBusy()) return false;   // ② 演出期间当成没点（见下）
  targetingItem = null;
  onAct(action);                  // 就这一句 —— 本地什么都不演
}
```

- 画面上"我这一手"**由服务端回放的那一步演出来**（`playNewEvents()` → `handleEvent()`）：
  枪口火光、音效、伤害数字、震动、横幅、对局记录**全都在那里出，一条都不能省**
  —— 省掉就是"枪响了但没人掉血"或者"点了没反应"。
- **`playOptimistic()` / `isOptimisticStep()` / 一次性标记 `optimistic` 已经整段删除**，
  连 `handleEvent(e, opt)` 里的 `skipOpen` / `openSound` 两个开关也一起删了
  （它们只服务于预演）。⚠️ **别再引入"恒为 false 的跳过开关"**：那种半死代码最恶心的
  失败方式是"某个音效被永久吞掉"，界面看起来一切正常，谁也不会去查。
- **为什么删**：用户实测**快速连点会把画面演成"所有人都被打死了"**。预演只演"起手"，
  真正的结果由服务器一条条回放，两条时间轴叠在一起就成了"我一边点、所有人一边死"。
  本机往返只有几毫秒，预演本来就没多少收益；用户明确说"卡一点就卡一点没事的"。
- **单机/联机都要演**：`playNewEvents()` 是两边共用的一条路（§3.2），
  删掉预演之后**没有任何一条路径可以绕过它** —— 这正是"两边都不会少演"的保证。

#### ② 演出期间锁住输入 —— 判据只有一个：`FrpAnim.busy()`

服务端那一帧**早就把回合推进过了**（一次 `room.act` 里 AI 的整个回合都同步跑完了），
而画面上那几步还要 450–700ms 一步一步演完：这段时间按钮显示的是"轮到我了"，
屏幕上演的还是上一步。不锁就是用户第 2 条反馈的原话 ——
"还没演完操作权就又回到用户层了，用户层几乎可以一直持续操作"。

**判 `busy()` 的位置（两处，缺一不可）**：

| 在哪 | 判它的理由 |
| --- | --- |
| `board.js` 的 `doAction()` / `onCardClick()` / `onSeatClick()` | **所有动作入口的总闸**。"当成没点"要做彻底：`onCardClick()` 那条"先点开道具、再选目标"的支路**不发消息但会改界面状态**（卡片点亮、动作区换成"选目标"），所以它也先判一次 —— 演出期间连"选目标"模式都不许进 |
| `app.js` 的 `submitAction()` | 它才是**真正发 `room.act` 的人**。牌桌判过不等于这里安全：将来多一条调用路径（或有人从控制台调），消息照样发得出去。判据本体只有一份：`board.js` 导出的 `animBusy()`，`app.js` import 它，**不抄第二份实现** |

两条纪律：

1. **为真时当成没点**：不发消息、不改界面状态（`targetingItem` 一个字节都不动），返回 `false`。
2. **房间级操作不受影响**：开始 / 离开 / 邀请好友 / 加人机走的是平台外壳，压根不经过
   这两个函数；对局内的 ☰ 菜单和「对局记录」展开条也没锁
   （看动画的时候正好想静音、想离开）。

**CSS 那一半**在 `css/style.css` 末尾第 7 节：演出期间平台给 `<body>` 挂
`frp-anim-busy`，本作据此把**会发 `room.act` 的两类控件**变灰 + `pointer-events: none`：

```css
body.frp-anim-busy #screen-game .actions .act-btn,   /* 开枪 / 二次选目标 */
body.frp-anim-busy #screen-game .hand .card { … }    /* 出道具（含"先点开再选目标"） */
```

⚠️ **只灰这两类**：房间级按钮不在这里；`.seat` / `.avatar` 也**刻意不灰** ——
那是平台的互动（扔鸡蛋/鲜花）入口，和"发 `room.act`"无关，锁了等于顺手砍掉一个平台能力。
⚠️ **CSS 只是视觉与命中测试那一半**：`el.click()`（DOM 直接派发）不受 `pointer-events`
影响，**只有 JS 那道闸拦得住它** —— 用例正是这么钉的（见下）。

#### ③ 单机也锁

牌桌是单机/联机共用的（§3.2），`doAction()` 一并管住了：本地结果虽然是同步回来的，
演出队列照样要演 450–700ms。
⚠️ 单机那 950ms 的"电脑思考感"（§3.3）是另一回事，别混。

#### 用例怎么钉的（`tests/browser.e2e.mjs` 的 4c-A / 4c-B 两节，都在真浏览器里）

- 观测手段（都在页面里，包一层计数器）：`GameNet.send` 数发出去的 `room.act`；
  `AudioContext.createOscillator` 数"这一下有没有出声"（`sfx` 是模块私有的，外面取不到）；
  `#fx-layer` 里的节点数枪口火光 / 伤害数字。
- **4c-A（不做预演）**：点击与取值放在**同一次页面求值**里 → 断言 `room.act` +1，
  而火光 / 伤害数字 / 振荡器 / 对局记录 / 横幅 / seq / 动作区 DOM **一个都没变**。
- **4c-B（演出期间点不动）**：先等 `FrpAnim.busy() === true`（服务端一次推来好几步时
  天然就是这个状态），断言 `<body>` 带 `frp-anim-busy`；再用平台自己的 `FrpAnim.push`
  排一条空步把窗口拉长到 1.6 秒（免得断言和定时器赛跑），然后**在一个求值里**把屏幕上
  所有 `.act-btn` 与 `.card` 全部 `el.click()` 一遍 → 断言 `room.act` 一个都没多发，
  seq / 动作区 / 手牌区 / 提示语 / 横幅 / 对局记录一个字都没变；
  同时量 CSS：`pointer-events === 'none'`、`opacity < 0.6`、
  按钮中心点的 `elementFromPoint` 不再落在按钮上（真手指点不进去）。
- ⚠️ **每个"真点击"之前都要 `waitIdle()`（等 `busy() === false`）**：`render()` 是同步的，
  按钮在演出还没演完时就已经在屏幕上了 —— 不等就点等于没点，用例会偶发失败，
  而且**失败得毫无线索**（seq 一直不涨）。第三个真人那一节找"谁来走这一步"的
  `canAct()` 也把"队列空了"并进了判据。

### 4.11 头像：语义圆环 + 平台互动（用户需求 3）

牌桌每个座位的 `.avatar` 上：

| 属性 / 类名 | 谁给的 | 作用 |
| --- | --- | --- |
| `data-frp-avatar="<id>"`、`data-frp-name` | 本作（`syncAvatar()`） | 交给平台的**事件代理**，头像自动可点 → 扔鸡蛋/鲜花、抛物线、碎裂、被扔提示**一行都不用本作写** |
| `is-me` / `is-human` / `is-bot` | `FrpReact.ringClass(id, isBot)` | 圆环颜色：**自己=蓝、其他真人=橙、人机=灰** |
| `data-color="0..3"` | 本作（原有的） | 降级成**头像底色**（原来是四色边框，会盖掉"谁是电脑"这条信息） |

- **颜色只在 `shared/ui/ui.css` 里定义**（三个游戏共用，用户点名要求一致）。
  本作的 `css/style.css` 只量尺寸（**52px**，≥44px 的硬指标）和那条底色 ——
  ⚠️ **不许在本作 CSS 里另定那三种颜色**，改了就是"这个不像亲生的"。
- **人机怎么判定**：只看 `p.isAI`（来自 `view.players[].isAI`，见 §4.3）。
  **不许按名字猜** —— 人机和真人共用同一张单字表。
  视图里没有 `isAI` 时一律当真人（橙）：那是老报文的兜底，宁可错成橙。
- **结算/记录界面里的头像**同样要带上这两个属性（同一套 `syncAvatar()`）。
- **区域限制**：点击热区就是头像本身。平台在 `document` 上用**捕获阶段**
  `preventDefault + stopPropagation` 抢 `[data-frp-avatar]` 的点击 ——
  所以**点头像不会再冒泡到座位的 `onSeatClick`**，本作原来那个
  "点对手头像选中目标"的捷径被平台吃掉了（选中目标仍然可以走动作按钮，
  而且"选择目标"模式下的覆盖层本来就在头像之上，点哪儿都是选中目标）。
- **音效/特效开关**（对局内菜单那两行）**只有一个数据源**：`FrpUI.prefs`（见 §4.12）。
  `board.js` 的 `syncPlatformToggles()` 负责把它接到平台（`FrpReact.setSound/setFx`、
  `FrpAnim.setEnabled`）—— 不然本作把音效关了、平台那边还在响。
- **扔鸡蛋/鲜花不许自己实现**：原项目那套 `REACTIONS` 已经删掉（见 §5），
  平台接管了。

### 4.12 音效/特效开关只有一个数据源；身份先用缓存顶着（D12 / D13）

#### ① 开关：`FrpUI.prefs` 是唯一一份（用户原话："平台设置栏的总开关和游戏里的开关不许打架"）

平台设置栏那个音效/特效开关，和本作对局内 ☰ 菜单那两行，**读写的是同一份东西**：
`shared/ui/ui.js` 里的 `FrpUI.prefs`（`localStorage` 的 `frp.prefs`，
接口是 `sound() / fx() / setSound() / setFx() / on()`，**已冻结、不许改**）。

本作原来是自己存自己的（`audio.js` 用 `sg.sound`、`effects.js` 用 `sg.fx`），
于是出现"平台开着、游戏关着"的局面：用户在两处各关一次才算真关掉，而且关哪个都不算数。

现在的接法（三处，都在本作里）：

| 文件 | 干什么 |
| --- | --- |
| `js/ui/audio.js` | `this.enabled` 的初值取自 `prefs().sound()`；`setEnabled(on)` 只写 `p.setSound(on)`（**不再碰 `sg.sound`**）；新增的 `syncPrefs(on)` 是**只同步、不回写、不出声**（启动时对齐界面用） |
| `js/ui/effects.js` | 同款：初值取自 `prefs().fx()`，`setFxEnabled(on)` 写 `p.setFx(on)`，新增 `syncFxPrefs(on)` |
| `js/ui/app.js` | `bindPrefs()`：启动时 `syncPrefs` / `syncFxPrefs` 对齐一次 + 刷新菜单上的文字，然后 `ui.prefs.on(...)` 订阅 —— 用户在**平台设置栏**改，本作立刻跟着变（反过来也一样） |

⛔ **红线**：

- `sg.sound` / `sg.fx` **只读一次**（`FrpUI.prefs` 内部的 `LEGACY` 迁移老值用），
  **别再往里写**。再开第二个数据源，就是回到"两边打架"。
- **别动"点一下才解锁声音"那条机制**（`audio.js` 的 `ensure()` / 懒 AudioContext）：
  浏览器规定没交互不许出声，绕过它只会变成静音或者控制台报错。
- **别把"特效关闭"做成"演出时长 0"** 之外的东西：`FrpAnim.setEnabled(false)` 会把每步
  压成 0ms（队列立刻排空），**但"逐步同步/锁输入"两套判据照样成立** ——
  `browser.e2e.mjs` 的 4c-B 就是靠这条抓"有人把开关接错了"（那时占位空步的 `busy()` 会是 false）。
- `fx` 的默认值是 `!prefers-reduced-motion`（用户系统里开了"减弱动态效果"就默认关特效）；
  `sound` 默认开。别自己另定默认值。

> **改成那样会怎样坏**：回到两个数据源之后，平台设置栏显示"音效开"，游戏菜单显示"音效关"，
> 用户点一下游戏里的开关只是**把两个都翻一遍**（看起来像失灵），
> 而刷新页面之后又会跳回另一个值 —— 这种 bug 不会报错，只会让人觉得"这游戏坏了"。

#### ② 身份：权威 → 缓存 → `/api/me`（D13）

公网握手要 2~3 秒，页面一打开先用 `GameNet.cachedMe()`（`localStorage` 的 `frp.me`）把
名字/ID **瞬间**显示出来，优先级是：

```
GameNet.me（WebSocket 的 ready，唯一权威）
  → GameNet.cachedMe()（本地缓存，只用于显示）
    → /api/me 的返回（最后兜底，401 就 location.replace('/')）
```

⛔ **红线（D13）**：缓存**只用于显示**。不许拿它填 `GameNet.me`、不许拿它判断"我登录了没有"
—— 登录态永远由服务端说了算。`tests/login-race.browser.mjs` 用"迟到的 401"把这条钉死了
（拿缓存当登录态的话，被登出的用户会看到一个"已经登录"的界面，然后在发消息时才莫名失败）。

> **改成那样会怎样坏**：把缓存写进 `GameNet.me` 之后，`shared/net/net.js` 里所有
> "我是不是登录了"的判断都会开始相信一个本地的旧字符串 ——
> 退登/换账号/会话过期全都不生效，而单机玩法看起来一切正常。

## 7. 实测覆盖与**没覆盖到**的地方

**实测过了**（`browser.e2e.mjs`，两个真浏览器实例）：

- 平台上真表单注册 → 领 ID → 进游戏页，`GameNet.connected` 真的连上
- 单机【人机对局】真的走了一步，AI 跟着动，**牌桌圆环是"1 蓝 + 1 灰"**
  （自己=蓝、电脑=灰 —— 身份标记从 `match.js` → 引擎座位 → `view.isAI` 一路通到界面）
- 【在线对局】建房 → 6 位房间号 → **第二个真浏览器用房间号 join 进来**
  → 房主开局 → 两边都切到牌桌、看到的座位一致
- 谁轮到谁点，点完**两边都收到同一帧服务器推送**（seq 相同）
- **一个人建房 → 座位 1 / 4、「开始游戏」灰着、旁边写着"至少要 2 个座位…
  按「添加人机」补一个"**；随后**绕过灰按钮直接发一条 `room.start`** →
  服务端拒绝 → 界面弹出提示条（"座位不够：至少要 2 个座位…"）且没有进牌桌。
  这一段验的是平台链路"服务端拒绝 → `shared/ui/room.js` 的 `Net.on(T.ERROR)` → 提示条"
- **按一下「＋ 添加人机」→ 成员列表多一行 `.frp-avatar.is-bot`（灰环）+「人机」标签
  + 单字名字（来自 `meta.botNames`）→ 座位 2 / 4、按钮解禁 → 开始 →
  牌桌上出现那个人机座位 → 真的等到"轮到我"→ 走一步 seq 变大**
- **牌桌头像逐个量过**：`data-frp-avatar` / `data-frp-name` 都在、点击区 52px ≥44px、
  圆环恰好是自己(蓝) + 人机(灰)
- **不做本地预演**（4c-A，用户需求 2 前半条）：点击与取值放在**同一次页面求值**里 ——
  `room.act` **0 → 1**，而火光 / 振荡器 / 伤害数字 / 记录 / 横幅 / seq / 动作区 **一个都没变**
- **演出期间点不动**（4c-B，后半条）：回包后 `FrpAnim.busy() === true` 且 `<body>` 带
  `frp-anim-busy`；用一条 1.6 秒空步把窗口拉长，再**在一个求值里**把所有动作按钮与手牌
  `el.click()` 一遍 —— `room.act` **1 → 1**、界面一个字没变；CSS 实测 `pointer-events: none`、
  `opacity: 0.45`、按钮中心 `elementFromPoint` 不落在按钮上。⚠️ `el.click()` **不受
  `pointer-events` 影响**，所以这条真正钉的是 JS 那道闸（§4.10）
- **逐条演出**：一次推来的多条事件**分 4 次**长起来（同步老写法只有 1 次，立刻红）
- **逐步同步**（4c-D，用户报的 bug）：演到一半采样 38 次，**27 次停在演出中途**、
  **18 次明显不是最终结算值**，且每次的弹药数 / 血量点 / 回合数 / 轮到谁**都等于那一步的补丁**；
  排空 + 对账后整块牌桌**等于权威视图** —— 老写法下这条当场红
- **单机也按步走**（同一个 `render()`）：这一手排进队列 **2 步**（序号 3/4）、
  **点完那一瞬画面停在第 3 步，不是最终第 4 步**
- 第二间房（2 个真人）：座位 2 / 4、「开始游戏」可点、新房间里**没有**上一间房的人机；
  **客人那边是只读文字（"人机由房主添加"）、没有任何能点的控件**
- **开局回放**（2026-10，**用户这一轮报的 bug 之一**）：`assertOpeningReplayed()` 在
  两处都跑过 —— 单机【人机对局】实测「对局记录第一条是『第 1 轮 · 实弹 3 / 空弹 2』」，
  「1 真人 + 1 个人机座位」实测「第一条是『第 1 轮 · 实弹 5 / 空弹 1』」。
  老写法下这条**永远不会出现**（开局那几步在玩家拿到第一帧之前就被服务器跑完了，
  §4.9.1），所以这条用例是老 bug 的硬证据，不是"顺手加的断言"。
- **对局中的底部弹窗**：`browser.e2e.mjs` 有一段"用了放大镜/手铐之后，
  底部提示条不许再冒出来"的采样（每 40ms 采一次 `.frp-toast` 文本、共 1.6 秒）。
  实测**这一局手里没有放大镜，用例打印原因后跳过** ——
  也就是说这条防线**还没在真浏览器里真正触发过一次**（见下面"没覆盖到"）。
- 服务器推下来的 `view` 里搜不到 `shells` / `drawPile` / `discard` / `seed` / `knowledge`
- 控制台零报错；430×932 与 360×640 下无横向溢出、点击区 ≥44px

**没覆盖到 / 不确定的地方**（如实写在这里，别当成已经验过）：

- **多人（3–4 个真人）只测了 2 人。** 3、4 人的座位分配、轮流顺序、以及
  "3 个真人 + 1 个人机座位"这种混合桌，由 `sim.mjs`（每人数 3000 局）、
  `ai-fill.test.mjs` 与 `rules.test.mjs` 的服务端用例覆盖，
  但**没有 3 个真浏览器一起打过**。
- **"1 真人 + 1 人机座位"在浏览器里只走了一两步。** 打到分出胜负、结算界面正确，
  是靠 `ai-fill.test.mjs`（服务端整局）与 `sim.mjs`（9600 局自对弈）保证的，
  不是靠浏览器。
- **"点头像扔鸡蛋"没在浏览器里点过那一步**：只验了头像上的
  `data-frp-avatar` / `data-frp-name` 与 44px 热区都在（平台的互动是**代理**，
  真点下去会弹菜单、发消息给服务端）。两端同步、抛物线、被扔提示属于平台层，
  由平台自己的 `tests/room.browser.mjs` 覆盖。
- **单机牌桌的"锁输入"没有单独的浏览器断言。** 4c-A / 4c-B 两节都在**联机**牌桌上量
  （单机那一局只验了"点一步真的走了 + 逐条演出"）。单机与联机共用同一个 `doAction()`
  （§3.2 那条"两边走同一条路"），但"共用"是**读代码**看出来的，不是实测到的。
- **人手快速连点没在浏览器里复现。** 用户报的场景是"点击太快 → 画面上所有人都被打死"。
  用例里点的是 `el.click()`（DOM 直接派发，比手指更快也更确定），
  真正拦住它的是判据本身（`busy()` 一来就当成没点），与点击来源无关；
  而"多快的手速才会出问题"这种量在无头浏览器里不好复现
  —— 原来那条"本地预演"的坏味道已经整段删掉了，不需要靠手速去触发。
- **掉线/重连没在浏览器里试过。** `removePlayer` → AI 接管由 `rules.test.mjs` 与
  `ai-fill.test.mjs` 覆盖（真人离座、人机座位传进来、重复调用、唯一真人离座四条）。
  真断网、真刷新恢复座位这条路径没实测。
- **"中途刷新 / 再来一局不回放旧事件"没有浏览器断言。** §4.9.1 那条 `reset` 分支
  （进页面时日志窗口里已经有几十条旧条目、"再来一局"之后 `seq` 从 0 重来）是
  **读代码 + 推演**得出的，本次没有真做"演到一半按 F5"和"再来一局立刻看画面"这两步。
  它的失败症状很显眼（血量点 / 弹药数当场算错），下次碰这块时值得补一条用例。
- **平台设置栏的总开关 ↔ 游戏内开关的联动没实测。** 本作这一半改成了只读写
  `FrpUI.prefs`（§4.12），"两边不会打架"是**读代码**看出来的；
  平台设置栏那一半由 `npm run test:browser` 覆盖（它点的是平台那个开关）。
- **身份缓存（D13）只验了"名字/ID 显示得对"**：`browser.e2e.mjs` 里页面一打开就注册进游戏，
  `/api/me` 与 WebSocket 都很快，**没有量过公网那种 2~3 秒握手时"缓存先顶上"的效果**。
- **"补丁里没有隐私"只在 Node 侧逐字段验过**（`rules.test.mjs` 的两条新用例）。
  浏览器里只搜了整份 `view` 的关键字（`shells` / `drawPile` / `discard` / `seed` / `knowledge`），
  **没有把日志里每一步的 `s` 也逐个搜一遍**。
- **真机手机没试过**（只有 CDP 的 360×640 视口模拟）。
- **提示条是按文字匹配断言的**：`browser.e2e.mjs` 找的是提示条文本里的
  "座位不够：至少要 2 个座位"（这是 `server/rooms.mjs` 的 `start()` 原话）。
  平台要是改了提示条的 DOM 结构（现在只认 `.frp-toast`）或者那句文案，这条用例得跟着改。
- **"事件序号 `n` 单调递增"这条去重契约**由 `sim.mjs` 与引擎侧用例保证；
  `browser.e2e.mjs` 只间接验了"分多次演 + 最终条数对得上"。
- **逆转器的"公开统计不许变"只在 Node 侧验过**（`rules.test.mjs` 的两条）。
  浏览器里**没有量过**"用了逆转器之后上方那颗统计有没有动" ——
  也就是说用户报的这个漏洞，防线是**规则单测**，不是实机观测。
  下次动 `remainingCounts()` / `faces` 时，浏览器那条要在真局里摸到逆转器才补得上
  （用例里发牌是随机的，摸不到就跳过）。
- **开局回放只验了"第一条是『第 1 轮』"这一件事。** 没有逐条比对开场那几步的顺序、
  没有验座位号显示与行动顺序一致、也没有量过"整段开场回放演了多久"
  （理论上一局开局可能排好几步，步数多时第一次能出手会等更久 —— 只在单机/1 人机的开局量过）。
- **"对局中不再弹底部提示条"这条在真浏览器里还没触发过。** 那段用例要手里**恰好有放大镜**
  才会执行（发牌随机），实测这一局没有，于是打印原因后跳过 ——
  **"删掉之后不再出现"目前是读代码 + 单机实测得出的，不是浏览器实测。**
  真要钉死它，得在用例里给页面塞一个已知手牌（或改成"只断言 1.6 秒内 `.frp-toast`
  没出现"、不依赖手牌）。
