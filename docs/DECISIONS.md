## D1 联机全部走自己的服务器，不再用公共 MQTT / WebRTC

**决定**：删掉三个原游戏里"公共 broker 当房间与信令通道 + WebRTC 打洞 + 中继降级"那一整套
（约 145 KB），改成客户端只连自己这台服务器的 `/ws`。

**为什么**：那整套存在的前提是"玩家没有公网 IP、也没有服务器"。现在有了 SakuraFrp 隧道，
前提没了。而且依赖公共 broker 带来一串真实踩过的坑：QoS0 没有 ack、
直连断了会被误判成"对手走了"、broker 有每 IP 连接数限制、公共话题上有人偷听要靠 `sid` 定向、
两端各自重放一手棋导致静默不同步。这些坑**整类消失**。

**否掉的选项**：
- 保留 WebRTC 直连（延迟更低）—— 收益很小（棋盘类游戏对延迟不敏感），
  代价是保留一整套打洞/降级/状态判定代码和它的坑。
- 自建 TURN —— 免费公共 TURN 实测已失效，自建要额外一台公网机器，没必要。

## D2 服务端权威

**决定**：游戏规则引擎跑在服务器进程里（`games/*/js/engine/**` 被 `server/games/*.mjs` import），
客户端只发操作意图、只收按人裁剪过的视图。

**为什么**：这是**唯一**的防作弊手段。两端各自跑规则的模型里，客户端改一行代码就能
"看到对手的手牌"或"走一步不合法的棋"。

**代价与对策**：引擎必须零 DOM、必须是原生 ESM（服务器和浏览器 import 同一份文件），
由各游戏自己的规则用例与 `npm test` 把关（平台不再提供 `check-game` 脚本）。

**人机对局是例外**：它在浏览器本地跑同一份引擎（困难档要占主线程 1.5 秒，
不值得发给服务器，也不该阻塞别人的房间）。因为没有隐藏信息、又不是对抗真人的场景，
本地跑不影响公平。

## D4 不做聊天（任何形式）

**决定**：平台和三个游戏里都没有聊天框、没有快捷短语、没有表情广播。

**为什么**：用户明确要求。而且一旦有聊天就要处理屏蔽、举报、刷屏、跨房间串话，
对一个"给自己和朋友玩"的平台来说完全不值得。

**替代**：好友列表 + 一键批量邀请 + 房间号已经够约局了。

## D5 身份来自账号，游戏不再问名字

**决定**：注册时取一个**单字名**（可以重复），系统再分配一个**7 位不可改的唯一 ID**。
游戏内部所有"取单字名"的界面和校验全部删除，`window.GameNet.me` 是唯一身份来源。

**为什么**：游戏里再问一次名字，就会出现"平台叫甲、房间里叫乙"的分裂，
而且好友系统是按 ID 认人的，名字重复也不影响。

**已定**（用户答复）：单字名要出现在**房间座位列表 + 对局中的牌桌/地图头像**上；
**平台首页的好友列表不用改**。

## D6 存储用 `node:sqlite`，不引入任何第三方运行时依赖

**决定**：`node_modules` 保持不存在。WebSocket 服务端手写在 `server/ws.mjs`
（Node 只有 WS **客户端**，没有服务端）。数据库用 Node 24 内置的 `node:sqlite`。
密码用内置 `crypto.scrypt`。

**为什么**：用户不是程序员，出问题时不能让他去 `npm install`；
而且依赖越少，"放了半年还能直接跑起来"的概率越高。

**代价**：`server/ws.mjs` 要自己实现 RFC 6455 的一个子集。
对策：`npm run test:browser` 用**真 Chrome** 连一次 ——
自己写的客户端和自己的服务端互测会一起错，真浏览器连上才算数。

**想换 `ws` 包必须先问用户。**

## D7 服务端手动开关 + 登录时自启（用 HKCU Run，不是计划任务）

**决定**：
- `start.cmd` / `stop.cmd` / `status.cmd` / `restart.cmd` 四个双击就能用的快捷方式，
  底层是 `tools/service.mjs`。
- 开机自启用**当前用户的 `HKCU\...\CurrentVersion\Run` 注册表项**，
  内容是 `wscript.exe "<仓库>\tools\run-hidden.vbs"`（隐藏窗口启动，不弹黑框）。

**为什么自启选了注册表而不是别的**（三条路都实测过）：
- ❌ `schtasks /Create /SC ONLOGON` → 系统回**"拒绝访问"**，建计划任务要管理员权限。
- ❌ 启动文件夹放 `.vbs` → 系统**拒绝写入**（同一个文件夹写 `.txt` 却成功，
  是安全策略在拦脚本文件）；换 `.cmd` 会闪一下黑窗口。
- ✅ `HKCU\...\Run` → 不需要管理员，写入成功，而且**任务管理器 → "启动"页能看见**，
  用户自己能禁用，不用记命令。

**⚠️ 自启是"登录时启动一次"，不是看门狗。** 用户手动 `stop` 之后，
服务会一直保持关闭，直到下次登录。

**为什么刻意不做看门狗**：用户明确说"有时候会跑其他工作，防止后台跑服务器占用后台"。
他要的是一个能真正关掉的开关，不是一个关了还会自己爬起来的服务。
**别改成守护进程。**

**校正过一次误解**：用户以为"改成开机自启就不会占 7891 端口了"。不是的 ——
服务在跑就占着端口。自启只是把"什么时候起来"从手动改成登录时，
所以**想要不占端口就得 `stop.cmd`**。

## D8 加好友需要对方同意（申请-同意制）

**决定**：`friend.add` 从"立刻双向生效"改成"**发一条申请**"。新增三条消息：
`friend.accept` / `friend.decline` / `friend.cancel`（撤回自己发出的）。
`friends` 全量快照扩展出 `incoming`（别人发给我的待处理申请）和 `outgoing`（我发出去的）。
协议表见 `docs/ARCHITECTURE.md`。

**为什么**：用户明确要求"加好友需要对方同意"。改之前的行为是单向即加 ——
任何人拿到你的 ID 就能把你塞进他的好友列表，而且**你这边也会同时出现他**，
你没有任何拒绝的机会。

**否掉的选项**：
- 保留单向即加、再加一个"忽略"按钮 —— 不满足"需要对方同意"。
- 申请只放在内存里 —— 服务重启就全丢，用户会以为"我明明发过申请"。
- 好友表改成存方向（"我加了他"≠"他加了我"）—— `listFriends` 和所有
  依赖它的上层代码（邀请、在线状态推送、好友列表界面）都要跟着改，
  而用户要的只是"加之前问一句"，不值得把好友模型整个翻掉。

**顺带定的两条**（用户原话里没有，但不定就会卡住）：
- **双方同时互相申请 = 直接成为好友**。两个人各点一次"加好友"，谁也不是"第二个同意的人"，
  不特判就会双双停在"等待对方同意"上，永远加不上。
- **重复申请**：回一句中文错误"已经发过申请了，等对方同意"（不静默、也不重复插行 ——
  `(from_id, to_id)` 是主键）。静默的话用户会以为按钮坏了。

**没做的**：申请数量上限 / 频率限制。项目里别处也没有限流；玩家 ID 是 7 位、
约 275 亿种，别人猜不到你的 ID。真被骚扰了再加。

## D9 人机是"坐在座位上的人"，不是"补几个电脑"

**决定**：人机成为**房间层的一个座位**。房主在准备区按一下「＋ 添加人机」就多一个座位，
再按一下（或点「移除」）撤掉。协议新增 `room.bot.add` / `room.bot.remove`，
`room.state.members[]` 带 `isBot`，房间状态新增 `minSeats` / `maxSeats`。
**`options.aiFill`（各游戏自己那套"补几个电脑"）整条作废**，三个游戏一起删掉。

**为什么**：用户明确要求"不要用选择加入几个电脑的方式，统一为按钮按一下加一个人机（坐在座位上）"。
老做法有三个真问题：

1. **看不见**。aiFill 是个数字，选完什么都不会发生；座位列表里也没有它。
   用户不知道"到底加上了没有"，也不知道人机叫什么、坐在哪儿。
2. **三个游戏三套 UI**。一个下拉、一个按钮组、一个滑块，用户每换一个游戏就要重新学一遍。
3. **和"真人优先"打架**。老做法是"开局那一刻按数字造人机"，所以人机是**开局时**才存在的；
   座位是**准备时**就存在的东西，两者本来就该是同一个概念。

**落地后连带的三条**（不定就会卡住）：

- **真人进房先顶掉最后加的那个人机**。座位满了还能不能让人进来？必须能 ——
  否则房主加满人机之后朋友就进不来了，那不就成了"人机占着位置不让真人玩"。
  被顶掉的是**最后加的那个**（最可能是刚手滑多按的），而且人机随时能再加回来。
- **开局门槛改成座位数**。老代码是 `room.members.size < meta.minPlayers`（只数真人），
  于是"一个人 + 一个人机"根本开不了局 —— 而这正是用户要的玩法。
  现在门槛是 `players.length < minSeats`（人机也算座位），
  `minPlayers` 只在游戏没写 `minSeats` 时当回退值，**不再单独当门槛**。
- **人机名字沿用单机那套单字池**（用户要求）。有自己 AI 名字池的游戏把池子导出成
  `meta.botNames` 复用，没有的游戏用平台默认池（`shared/protocol.mjs` 的 `BOT_NAMES`）。
  同一间房里不重名。

**否掉的选项**：

- 只改界面、服务端继续按 aiFill 造人机 —— 人机不会出现在成员列表里，
  也就没有"座位"这回事，用户点不开它的头像、扔不了鸡蛋、也看不出它是不是人。
- 让游戏自己加人机座位（`room.bot.add` 里带 game 自定义逻辑）—— `rooms.mjs`
  不许认识具体游戏（架构铁律），一律走 `meta`。

## D10 演出队列 + 演出期间锁输入（**不再做本地预演**）

**决定**（2026-10-20 晚按用户实测反馈改过一次，下面是改完的版本）：

1. **不做本地预演。** 玩家点下去之后，到服务器回包之前**本机不播任何动画、不出任何音效**。
   画面上"我这一手"是由服务端回放的那一步演出来的。
2. **服务端推下来的每一步按顺序一个个演完**（`shared/ui/anim.js` 的 `FrpAnim`），
   每步 450~700ms。**刻意不支持点击跳过、也不快进**（用户明确要求"逐个演完"）。
3. **演出期间锁住输入。** 队列没排空时：
   - 游戏在提交口子上判 `FrpAnim.busy()`，为真就**不发消息**（当成没点）；
   - 平台给 `<body>` 挂 `frp-anim-busy`，游戏用自己的 CSS 把动作控件变灰/禁点。
   房间级操作（开始 / 离开 / 邀请 / 加人机）不受影响。

**铁律**：**绝不在本地改权威状态**。血量、胜负、回合、牌堆一律以服务端推来的 `view` 为准。

**为什么把"乐观演出"删掉**（原来的 D10 就是那一版，留作教训）：

- 用户实测：**快速连点会把画面演成"所有人都被打死了"**。预演只演"起手"，
  可连点会连着演好几下起手，而真正的结果由服务器一条条回放 ——
  两条时间轴叠在一起，看起来就是"我一边点、所有人一边死"。
  本机往返只有几毫秒，预演本来就没多少收益；**用户明确说"卡一点就卡一点没事的"**。
- 用户第 2 条反馈：**演完之后操作权才该回来**。原来演出是异步的，
  服务端那一帧早就把回合推进过了，所以玩家能"一边看动画一边接着操作" ——
  画面和操作错位，这正是上一条那种乱象的土壤。现在演出期间输入被锁住。
- 用户第 4 条（"别等服务器验证"）**按实测结果被否掉了**。当时的理由是公网往返 100~300ms，
  但"看起来快"换来的是"看起来乱"，不值。**代价是点下去要等一个来回才有反应，用户接受。**

**仍然保留的**：服务端**同步**跑完 AI（D2 / 「游戏模块接口」）—— 那是房间层没有定时器决定的，
和这里的客户端演出无关；一次推来多步这件事没变，变的只是客户端怎么对待它们。

**否掉的选项**：

- 把 AI 拆成"一步一步慢慢来"（服务端加定时器逐条推）—— 要动 D2 那条铁律，
  而且断线重连、超时判负、房主离开这些路径全都要重写；风险远大于收益。
- 客户端做"点击跳过" —— 用户明确说不要。
- 客户端本地跑一份引擎来"预演"对手的隐藏信息 —— 那本就是防作弊要防的东西。
- **保留预演 + 只锁演出期间的输入** —— 预演发生在"点击→回包"这段窗口（此时队列是空的，
  锁不住），它和回放是两条时间轴，叠起来照样乱。所以整条预演都删掉了。

## D11 互动是平台能力，不是游戏功能

**决定**：扔鸡蛋 / 送鲜花做成 `shared/ui/react.js` 一件共用能力 + 一条协议
（`react.send` → `react` 广播），并且**不限次数**（用户明确要求）。

**为什么**：三个游戏原项目里各有一份"点别人头像扔东西"，但那是"没有服务器时顺手做的
一条广播通道"，搬迁时整块删掉了（旧规范 D12 那批禁止清单）。现在有服务器和房间，
这件事应该只做一次：用户在任何一个游戏里学到的"点头像 → 扔鸡蛋"必须完全一样。

**接法**：游戏给头像元素加 `data-frp-avatar="<玩家id>"` 就自动可点（事件代理，
SVG 也认）；扔的时候服务端把这一条广播给**房里每个人（含发起人）**，
发起人靠回执里的 `rid` 认出自己的回声、不播第二遍。

**两条技术性防刷**（不是玩法限制，用户要怎么扔就怎么扔）：
服务端 2 秒 40 条之后**静默丢弃**（`REACT_BURST`），客户端同屏特效节点上限 20 个。
没有这两条，一个客户端（或一台卡手机）就能把整房拖垮。

**顺带定的**：圆环颜色是有语义的（自己=蓝、其他真人=橙、人机=灰），
三个游戏必须一致 —— 这是用户点名要求的，写进了 `docs/ARCHITECTURE.md` 的 DOM 契约。
不做"互动历史/统计"：没人要，而且会变成第二个聊天框。

## D12 平台外壳：底部三栏（只用图标）+ 平台只有一份音效/特效偏好

**决定**（用户逐条确认过）：

1. 平台首页（`web/`）改成**底部三栏**：🎮 游戏 ｜ 👥 好友 ｜ ⚙️ 设置，
   **只用图标**（选中高亮 + 略微放大），切换是**同一个网页内的栏目切换**、用**淡入淡出**。
   顶栏精简成一行「你：X · ID Y」；登出、身份（含复制）、连接状态都进设置栏；
   待处理好友申请在"好友"图标上给一个小红点；登录/注册仍是独立整页。
2. **音效与特效只有一份偏好**，存 `localStorage` 的 `frp.prefs`，读写入口是
   `shared/ui/ui.js` 的 `FrpUI.prefs`（`sound()/fx()/setSound()/setFx()/on()`）；
   平台设置栏和三个游戏里的开关都只是**这份偏好的入口**。
   平台自己的按钮音是 `FrpUI.sound.click()`（音色抄刀马那个 620→420Hz 三角波 60ms），
   平台外壳用 `FrpUI.sound.bindClicks()` 自动接，游戏**不要**接（会响两声）。

**为什么**：用户原话是"平台设置栏里有总开关，游戏里的开关跟随它，**两处不会打架**"。
在这之前每个游戏自己存一份（`cg.sound` / `bs.sound` / `sg.sound`），于是"平台开着、
游戏关着"这种局面迟早出现，而且用户没法在两处看到同一个状态。
图标不带文字是用户点名要的（"这样好看"）；**否定掉的**是横向滑动动画（用户嫌晃眼）。

**代价 / 注意**：

- 老键只在**第一次**读时用来定默认值（`ui.js` 里的 `LEGACY` 表），之后不再看 ——
  免得哪天删掉一个老键反而把用户后来的设置改回去。
- 平台那几条浏览器用例原来是按"好友面板在游戏下面、登出在顶栏"的旧结构点的，
  搬栏目必须同步改（**不许**为了过用例给旧元素留隐藏副本）。
- 三栏是**平台外壳**的事；游戏页里那块牌桌/棋盘不受影响（它们各自还有自己的栏目界面）。

## D13 身份先记住、再对齐：进游戏页不再等那 2~3 秒

**决定**：谁先把身份拿到手（平台外壳的 `/api/me`、WebSocket 的 `ready`）就**顺手记在
浏览器里**（`localStorage` 的 `frp.me`，读写入口 `GameNet.rememberMe/cachedMe/forgetMe`）；
游戏页一打开先用记着的那份把名字/ID 画出来，等 `ready` 到了再对齐。

**为什么**：平台首页和每个游戏页是**两个不同的网页**，点进游戏是一次整页跳转。
游戏页原来只能等 WebSocket 的 `ready` —— 公网那次握手实测要 **2~3 秒**（见 `docs/TUNNEL.md`
那一类链路结论），这段窗口里用户看到的是"正在确认身份…"，而且**点「开始对局」会被误判成
"还没登录"并弹出那句假提示**（用户实测撞到过，这是本轮修的一个真 bug）。

**红线**（不这么做就会坏）：

- ⛔ **不许拿缓存去填 `GameNet.me`、也不许拿它判断登录态**。平台外壳的登录竞态
  （迟到的 401 不许把界面翻回登录页，`tests/login-race.browser.mjs`）就是靠
  "**me 只有服务端说了才算**"成立的；预填会把它变成"先信本地、后信服务端"，用例立刻红。
  缓存只用于**显示**；权限永远在服务端，401 / 身份对不上就 `forgetMe()` 并按原逻辑回登录页。
- 平台外壳登出时也要 `forgetMe()`（否则下一个人在这台机器上会先看到上一个人的名字）。

**代价**：改名之后第一次进入游戏，可能有一瞬间显示的是旧名字（`ready` 一到就更正）。
这个代价换掉的是 2~3 秒的干等 + 一句假提示，用户确认接受。

## D14 逐步同步：服务器给每一步带上"这一步之后的状态"

**决定**：每个游戏的事件/播报条目都带一份**这一步之后的公开状态补丁**（服务器算好的），
客户端把补丁**逐步**应用到画面上 —— 演到第几步，血量/装备/位置/弹药/手牌/回合就变到第几步，
演完最后一步再用**权威视图**整体对账一次。

**根因**（用户这一轮的两条反馈都是它）：`render(view)` 一收到 `room.state` 就**立刻**按最终
状态重画整块界面，只有"播报 + 特效"进了 `FrpAnim` 串行队列 —— 于是"演出还在演，数字已经是
结果了"（恶魔轮盘的血量、刀马的装备/位置/倒计时，用户都点名过）。刀马那条"位置移动直接瞬移"
更具体：地图靠 `.token` 的 CSS transition 补间，而坐标在**收到消息的瞬间**就改了，
补间发生在演出之前。

**为什么状态必须由服务器给，不许客户端自己推演**：

- 铁律三：规则只有一份（服务器）。客户端"按事件自己算血量/位置"就是**在界面里重写一遍规则**，
  迟早和引擎对不上（而且改规则时两边会各自演化）。
- 防泄露：补丁必须过和视图**同一套**裁剪规则 —— 只放**这一刻本来就公开**的东西。
  ⛔ 恶魔轮盘的弹匣真实顺序、别人的手牌/放大镜情报；刀马未揭晓的猜拳选择，**都不许进补丁**。
  这一条有测试盯着（整份报文 JSON 化之后搜那些关键字，命中必须是 0）。

**被否掉的选项**：

- **演出期间冻结到"演完再一次性跳到结果"** —— 改动小，但中段会"只有演出、数字不动"，
  比现在更怪（用户看到的是"枪响半天没人掉血，最后一秒全掉"）。
- **只同步最重要的几项**（血量/位置），弹药/手牌等演完再跳 —— 用户明确选了"整块牌桌都按步走"。
- **服务器每步发一整份裁剪视图** —— 报文太大（一次 act 常有几十步）。

**兜底**：某条事件没有补丁（老报文 / 补丁缺失）时照旧演特效但不改数字，最后由对账收口；
完全没有补丁的报文走改动前的行为。**对账不许插队**：队列没排空时来了新视图，
要把对账推迟到队列真的空掉那一次，否则会出现"演到一半突然跳到结果"。

**顺带定的（刀马的倒计时）**：服务器每段限时 **+2 秒**（`REPLAY_BUFFER_MS`，
写在引擎常量里并注明用途），客户端**演出期间不显示在跑的倒计时**、队列空了才显示真实剩余。
用户原话是"倒计时缓冲个 1s"，取 2 秒是因为一轮演出常常 1~2 秒；实测断言是
"队列空的那一刻剩余时间 ≥ 标称限时的 90%"。⛔ 不接受的做法：把倒计时**锁住不推**
（`{kind:'tick'}` 是锁输入的唯一例外，锁了只会让超时白白晚几秒）。

**补一条实现时才浮现的规则（两个游戏都踩到，必须照做）**：
**首次挂载 / 重开一局时，一条旧条目都不许回放。**

- 补丁是**差量**（"谁变了"），没有基线就叠不出结果。而页面中途刷新、从平台好友卡片进来、
  重连恢复座位时，客户端拿到的第一份视图是**当前（最终）状态**，而事件/日志窗口里
  还挂着几十条旧条目、游标却是 0 —— 老实回放就是"把补丁叠在最终状态上"，
  **血量点/弹药数会当场算出错的数**（而且会莫名其妙演很久）。
- "再来一局"之后序号从 0 重来、旧游标比新序号还大，同理。
- 所以首次挂载或检测到序号回退时：**只画权威视图**（必须**强制**重画 —— 换局后权威序号
  比显示序号**小**，"已经追平就不画"那句会把上一局的画面留在屏幕上），游标直接对齐到
  当前窗口最后一条（"这些你已经看过了"）。**只有"上一帧之后新增的条目"才排队演** ——
  这正是"接上一局正在进行的对局"该有的行为。
- 代价（诚实记着）：进页面时看不到"这一局刚才发生了什么"的回放。这是刻意的：
  回放旧账既会算错数字，也不符合"我刚进来"的预期。

**唯一的例外（2026-10，恶魔轮盘实机反馈补的）**：**当头一帧的日志里第一条就是这一局的
第一步（`n === 1`）而且带着补丁时，要一条条把开场演出来。**

- 为什么判据只有这一条：一局的**第一条**补丁天然是**全量快照**（引擎的 `patchBase` 是
  按 state 对象存的 `WeakMap`，第一条取不到基线）—— 有基线，差量才叠得上去。
  "第一条不是 `n === 1`"（打了一半才进来、重连恢复座位、从好友卡片进来）**照旧一条都不回放**。
- 为什么需要它：恶魔轮盘的服务器在**广播之前**就把人机的整个回合同步跑完
  （`server/rooms.mjs` 没有"稍后再推一次"的机制），所以玩家拿到第一帧时已经轮到自己。
  用户原话是"**我明明在 3 号位，却是第一个行动**"—— 座位和回合一直是对的，
  是**开场那几步根本没演给人看**。
- 实现要点：先把第一条补丁（全量）贴到权威视图的拷贝上当地板，再把显示游标退回 0，
  然后照常排队 —— 第一条的 `n === 1` 正好接得上链（补丁只认 `n === 显示序号 + 1`），
  它的内容已经在地板里了，再贴一遍是**幂等**的。
- 代价：单机对局挂上牌桌时也会演一遍"第 1 轮 + 摸牌"，第一次能出手晚约 1 秒 ——
  与 D10 那句"卡一点就卡一点没事的"同一条口径。
- ⛔ **不许**用"把房主放到 1 号位"去糊这件事（座位故意是随机的，见 D9 那一带）。

## D15 对外通道：国内 TCP 隧道 + frpc 自动 HTTPS（Cloudflare/HTTP 那条停用保留）

**决定**：访客入口从 `https://<你的域名>/`（Cloudflare 小黄云 + 日本节点 HTTP 隧道）
换成 **`https://<你的公网地址>`**（国内 TCP 隧道 + 面板里开「自动 HTTPS」）。
旧那条**只停用、不删除**：配置归档在 `frpc/http/`，将来有公网 IP 或想要有效证书时可以再开回来。
**服务端代码一行都没改** —— 变更全在 SakuraFrp 面板与隧道配置。

**为什么**：Cloudflare 免费版把中国大陆访客甩到**洛杉矶**边缘节点 —— 实测
`https://<你的域名>/` 首字节 **1.34 秒**并返回 **503**（`CF-RAY` 带 `-LAX`）；
更要命的是那条"**约 12% 的新建 WebSocket 连接会一直卡到浏览器自己 60 秒超时**"（本机直连 0/9）。
换成国内 TCP 之后（实测见 `docs/TUNNEL.md` 第一节）：TCP 连接 **35~74ms**、整趟 87ms、
**30 次握手 0 次卡住**，两台真浏览器走完整盘在线对局全绿。

**必须一起做的事（实测踩出来的，不是可选项）**：国内节点**会拦截明文 HTTP**
（回它自己的 501 合规页，字节根本不转到本机）。官方速查表写着"**网页 + 国内节点 = 必须开自动 HTTPS**"。
开了之后 **TLS 在 frpc 里就终止、脱壳后仍用明文 HTTP 连本机 7891** ——
所以这一条**不违反**"服务端只监听明文 HTTP"的硬约束，反而正是它成立的前提。
细节见 `docs/TUNNEL.md` 坑五。

**代价（用户 2026-10-21 明确接受）**：

- 访客地址**带端口**（`:<端口>`）：SakuraFrp 免费隧道的远端端口是随机分配的，
  套不上 Cloudflare 那种 80/443 的路子。
- 访客**第一次打开会看到自签证书的警告**，要点一次「继续前往」（证书由 frpc 现场生成）。
- 没有 CDN：静态资源全部由这台电脑经隧道送出（限速 10 Mibit/s）。
- 换了域名，朋友要**重新登录一次**（cookie 按站点隔离）。
- 节点是单点，国内节点挂了没有备用路线（备胎就是那条停用的 HTTP 通道）。

**被否掉的选项**：

- **保留 Cloudflare / 继续调日本节点** —— 那就是问题本身（慢、503/522、12% 卡 60 秒），
  而且这几样我们这边都查不了（WS 升级请求不进我们的日志）。
- **给服务端加 HTTPS**（自己读证书）—— 要处理证书与续期，而且**直接违背硬约束**
  （服务端只监听 `127.0.0.1:7891` 的明文 HTTP）。TLS 该由 frpc 去终止。
- **把 TCP 隧道套在 Cloudflare 后面**（想拿回有效证书 + 免端口）—— 做不到：
  Cloudflare 免费版只能回源到源站的 80/443，而隧道必须带端口。
- **改用 `cloudflared`（Cloudflare Tunnel）** —— 免费、自带有效证书、不经过第三方节点，
  但中国访客**仍然要连 Cloudflare 的海外边缘节点**，延迟跟现在一样糟（换汤不换药）。
- **内地节点的 HTTP(S) 隧道**（连端口都省了）—— 内地建站要 **ICP 备案**，`<你的域名>` 没有。
- **为了免掉证书警告去买/申请一个自己的域名 + 真证书** —— 用户 2026-10-21 选择**先不折腾**：
  证书的域名必须等于访客输入的域名，等于还要让第二个域名也指到这台节点，
  而且免费证书 90 天要续一次。**留作以后的独立一轮**（想升级时看 `docs/TUNNEL.md` 第一节）。
- **双通道并行**（HTTP 与 TCP 同时对外）—— 多一套要维护、要盯的状态，
  而 HTTP 那条已经是 503，没有并行价值。

**顺带发现（不是这次改出来的，是公网延迟把它照出来的）**：
`Net.send`（`shared/net/net.js:405`）在 socket 还没 `OPEN` 时**静默 `return false`**，
而"创建房间"按钮（`shared/ui/room.js:275`）不检查它的返回值 ——
本机 1ms 就绪所以永远撞不到，公网上就是"点了没反应"。
这次只修了**测试的竞态**（`tests/room.browser.mjs` 点击前先等 `GameNet.connected`），
界面那一条记在 `docs/NEXT.md` 待办。

## D16 公开的弹药统计按"装填时那一面"记账（逆转器不许变成免费放大镜）

**决定**：恶魔轮盘的 `state.magazine` 多一份 `faces` = **装填时每一发的那一面**
（`reloadMagazine()` 写一次，之后**只读**），公开的「实弹 N / 空弹 M」统计**数 `faces`**；
逆转器只翻枪膛里的 `shells`，**不动统计**。

**根因**（用户实机原话）：

> "转换器功能有漏洞，我没有放大镜、不知道这一发子弹的真实情况，但我用了转换器后，
>  却可以看到上方子弹统计从'实弹 5 空弹 3'变成了'实弹 6 空弹 2'，
>  这间接告诉了我这一发子弹现在是实弹。"

原来统计数的是**枪膛里此刻那一面**，而逆转器翻的正是那一面 —— 数字一动就等于
**白送一次放大镜**（一次免费情报，规则里放大镜是要占一张牌的）。

**为什么不能让统计跟着翻**：这就是用户报的漏洞本身。逆转器是**公开动作**
（本来就知道这一发的人可以顺推新值），所以不能改成"只告诉使用者自己" ——
那会让同一个牌桌上出现两份互不相同的公开统计。

**代价（如实说）**：膛里那一发被翻过时，公开统计会与枪膛里那一发**故意不一致**
（统计说"还剩 1 实弹"，而膛里已被翻成空弹）。这是刻意的：宁可让统计慢一拍，
也不能让逆转器变成免费放大镜。它**最多只影响膛里那一发**（同一时刻只可能有这一发被翻过），
那一发打掉 / 退掉之后统计**立刻**又等于真实剩余；总数**永远**等于"枪膛里还剩几发"。

**被否掉的选项**：

- **统计跟着翻（旧行为）** —— 就是用户报的 bug。
- **干脆不显示实弹/空弹各有几发** —— 那是本作的核心公开信息（"实弹 2 / 空弹 3"决定敢不敢开枪），
  删掉等于改规则。
- **逆转器改成只对使用者可见** —— 它本来就是公开信息（弹药总数守恒，旁观者能顺推），
  改成私有会在同一张牌桌上造出两份不同的"公开"统计。

**回归防线**：`games/shell-gambit/tests/rules.test.mjs` 的「逆转器」两条用例
（公开统计一个字都不许动 / 翻过的那发离膛之后统计立刻变真）。
⚠️ 同一份文件里的 `setMagazine()` 辅助函数**必须同时写 `faces`**（少写它，
单测里逆转器又变回放大镜，而线上代码其实是对的）；`cloneState()` 也要带上 `faces`
（它做的是深拷贝，漏字段会在"先试后回滚"的用例里漂移）。
诚实记一笔：**浏览器里没有量过这条**（发牌随机，用例里摸不到逆转器就只能跳过）——
用户报的这个漏洞，防线是**规则单测**。

> ⚠️ **2026-10-22 之后的读者请注意**：D17–D27 是围着**已被删除**的自研《三国杀 Lite》写的，
> 它们引用的 `games/sanguosha-lite/tests/…` 这些"回归防线"**已经不存在了**。
> 这些条目留下来的价值是**判断与教训**（判据怎么定、什么算"测过了"、
> 哪些坑只有真浏览器才看得见），不是"跑去那里跑一遍就会绿"。

## D17 拼点泄漏从**源头**堵：已选牌不进 `ctx`，而不是"进 view 再裁"

**决定**：「已选牌」草稿存引擎**内部状态** `state._pindianDraft`（`js/engine/phases.js`），
**既不进 `pending.ctx`、也不进任何会被序列化的通道**；`pindianAnswer` 从那里读，
`choiceAnswer` 的拼点判据改成 `ctx.skill === null && ctx.step === 'pindian'`。
四处退出路径都清草稿（双方失效 / 无牌可选 / 开始新拼点时顺手清上一次 / compare 开头）。

**为什么**：原实现把整个拼点项塞进 `pending.ctx.pin`，而 `view.js` 的口径是
「`ctx` 只给 actor 本人」；拼点第二步的 actor 恰好是**对手** ——
于是他收到的 `ctx.pin.mine` 就是发起方刚选的那张手牌（实测那一帧 `pin.mine === 'std-0028'`）。
这违反铁律 2（隐藏信息绝不进报文）。修在源头的好处是：数据**根本不产生**，
也就不存在"哪天某个消费者忘了裁"。

**被否掉的选项**：

- **在 `view.js` 里把 `ctx.pin` 裁掉**（先上报文再裁）—— `ctx` 的裁剪口径是铁律 2 的宿主，
  在它里面加一条"拼点特例"等于把隐藏信息的裁剪逻辑从一处扩散到两处；
  以后拼点若支持多张牌，同一个坑还会再来一次。
- **留一处逐字豁免**（测试里把那条断言跳过）—— T7 的隐藏信息扰动用例当时就是这么绕过去的；
  T17 已把豁免删掉，现在那条断言是**真检查**且绿。
- **保留 `ctx.pin` 但只发给发起方** —— 第二步的 actor 就是对手，他取不到牌就答不了，功能直接坏。

**回归防线**：`games/sanguosha-lite/tests/view.test.mjs` 4 条
（亮牌前被拼点方 0 命中 / 反方向 0 命中 / 亮牌后双方都看得到两张牌 / 草稿用完即清）。
牙齿证明：把 `pin` 塞回 `ctx` → **2 条红**（连文件自带的 `assertFrameClean` 也一起被触发）→ 恢复 → 绿。
`js/ui/**`、`js/ai/**`、`server/**` 里 grep `ctx.pin` **0 命中**（没有消费者，界面与 AI 不受影响）。

## D18 人机能用**模式技能**，仍然禁用**武将技能**

**决定**：人机允许使用 `mode-skills.js` 注册表里的**模式技能**（【飞扬】【跋扈】【农民补偿】这类，

**为什么**：用户的原话是"不然每个武将单独适配一个人机体量太大了" ——

**被否掉的选项**：

## D19 减体力上限**最低为 1**（通行判法，不是官方原文）

**决定**：任何"减体力上限"的效果一律 `p.maxHp = Math.max(1, p.maxHp - n)`，
**随后把 `hp` 夹到上限之内**（不许出现 `2/1` 这种非法状态）。
理由与出处：资料把"体力上限减到 0 会怎样"标着**待核实**（`docs/research/sanguosha-generals.md`
的 §11.C#28 裁定表第 28 行 + 【崩坏】正文），**通行判法是上限最低为 1**，资料里**没有官方原文**。

**为什么**：引擎**需要**一个硬性下限 —— 上限 0 会让整条管线进入非法状态
（0 血 0 上限的角色怎么判濒死？回复上限、`maxHp` 画格子、手牌上限三处都得为它开特例）。

**被否掉的选项**：

- **允许上限减到 0**（照字面"减 1 点上限"）—— 会造出 `0/0` 这种状态，三处以上要开特例。
- **减上限时把玩家弄死**（另有一种判法如此）—— 资料里查不到这一条的依据，不发明规则。
- **既然没有官方原文就先不设下限** —— 会让同一份牌在不同实现里行为不同；
  宁可写成"通行判法 + 硬性下限"，并在注释里标明它是裁定。

**回归防线**：`games/sanguosha-lite/js/engine/skills/forest.js:46`（【崩坏】）与
`mountain.js:34`（山包同类效果）走同一行；`tests/skills.test.mjs` 的【崩坏】用例断言
`maxHp 2 → 1` 且 `hp` 被夹到 1（"不出现 `2/1` 这种非法状态"）；T14 的牙齿证明
（摘掉夹取 → 红 / 恢复 → 绿）。
⚠️ 这条同时也是 `AGENTS.md` 的登记项（T17 把三件套记在自己 output 里，由 T10 统一起草）——
DECISIONS 这里记的是"**为什么**、否掉了什么"。

## D20 牌桌**不随视口缩放**（44px 是无障碍红线）

**决定**：三国杀 Lite 的牌桌在任何视口下都**不缩放** —— 不用 `transform: scale()`、
不按视口缩头像、不按视口改卡面。实测尺寸（T8，4 个竖屏视口 × 单机 8 人身份局 / 联机 3 座，
共 8 组，全部在伪横屏的**旋转坐标**里量）：牌桌头像**自身** 46×46、
热区（`elementFromPoint` 中心点反查）46×46、当轮最小可点目标 44×44、
手牌 58×78、牌名 13px、花色点数 11.5px。

**为什么**：平台的浏览器用例在各游戏里实测多种视口，要求
**可点目标自身任一边 ≥44px**，`[data-frp-avatar]` 也在测量范围内，量的正是**元素自身**
而不是外层更大的壳。一缩放，小屏上的头像就掉到 44px 以下 —— 那是**现场判红**
（`games/sanguosha-lite/tests/browser.size.mjs` 会红，平台体检也会红）。

**被否掉的选项**：

- **`transform: scale()` 按视口缩整块牌桌** / **给小屏单独做一套更小的头像与卡面** /
  **用 `zoom` 或按视口改 `--card-w` 这类 CSS 变量** —— 三个都会把可点目标压到 44px 以下，
  而且会让"同一张牌在不同手机上看到的牌面/字号不一样"，
  "卡面在最小可点尺寸下仍可读"这条就无从谈起。
- **手里牌多的时候缩牌面**（而不是叠压）—— 也被否：合成 12 张 + `.is-tight` 复量，
  牌面仍是 58×78、字号仍是 13px / 11.5px（**只叠压、不缩牌面**有断言钉着）。

**代价（⚠️ 这是待修的缺陷，不是我们选的边）**：不缩放 + `#online-panel .board` 的高度
= `min(50dvh, 360px)`（设计文档 §9.7）⇒ **联机对局中牌桌整块比画面框高 34~74px**，
四种竖屏视口都超（实测：360×640 超 64px、375×667 超 63px、390×844 超 74px、430×932 超 34px），
小屏上自己的手牌/操作区要滚一下才看得到（实测表原样记在 `docs/NEXT.md` 的未决项里）。
**修法已定**：T21 —— 对局进行中把房间外壳（房号/成员/设置/开始）收起或浮层化，
留一个 ≥44×44 的入口可展开；⛔ 不许用缩放解决。
T8 顺手把"牌桌整块超出画面框时，往上**必须找得到能滚的祖先**，否则判红"写成断言 ——
那是**兜底**（保证滚得到），不是认可这个现状。

## D22 判据过期 ≠ 约束可以没有：从"对局记录贴底"换成"重画不扰动版面"

**决定**：设计文档 §9.7 第 4 条（平台观感四条之一）在本作**不改含义、只换可测的等价物**：
外壳每重画一次（`FrpRoom.render(true)`），手牌区 / 操作区 / 我的武将区 / 座位层的
`getBoundingClientRect()` **前后差 ≤1px**，且本身可滚动的容器（手牌横滚、判定区）
重画之后**滚动位置不许归零**。

**为什么**：原判据是"对局记录贴底"，但设计文档 **§9.3 已经把可滚动的对局记录侧栏砍掉**
（由中央演出区取代；`view.log` 保留给 AI 与用例）。判据**无处可测**了，
可它真正要防的东西还在：牌桌每次收到 view 都会重画，"重画时版面跳一下 / 滚动条归零"
是玩家看得见的问题（刀马 §17 那个 `_pinLog()` 坑就是同一类）。所以保住**意图**、
换成能量得出来的等价物 —— 这就是"判据过期 ≠ 约束可以没有"。

**被否掉的选项**：

- **因为判据过期就整条删掉** —— 约束没了之后，"重画跳版面"就变成"没规定"，
  下次谁都不知道该不该修。
- **硬留着"对局记录贴底"** —— 本作没有任何记录区，用例只能永远跳过 = 假覆盖。
- **改成"重画前后 DOM 结构一致"** —— 结构一致但位置跳，玩家的感受一点没变。

**回归防线**：`games/sanguosha-lite/tests/browser.e2e.mjs` 第 6 段
（强制重画 `FrpRoom.render(true)`，前后量四个区域的 rect 差与滚动位置）。
⚠️ 该文件由 T9 在做，本轮尚未收口 —— **这条防线以 T9 收口时的结果为准**。
出处：设计文档 §9.7 第 4 条（含"判据过期 ≠ 约束可以没有"的原句）；前身是刀马 §17 的 `_pinLog()`。

## D23 改"显示文案"也会打坏别的东西：「这段文字谁产的」必须可查

**决定**：界面凡是**直接显示引擎产的文字**（`view.log` / 待决提示 / 事件 label），
去匹配或解析它时**必须用与引擎同一个口径**。本作的口径是**武将名**
（回退规则也跟引擎的 `who()` 一致：`generalRevealed` 未亮 → 回退玩家名）。
并且**"这段文字是引擎产的还是界面拼的"要能在代码里一眼看出来**（注释写明
「日志兜底」还是「事件拼装」）。测试里断言"屏幕上该出现谁"时，
**玩家名与武将名都列出来再断言**，不许只查一个。

**为什么**：T22 只做了一件事 —— 把对局记录/待决提示的称呼从**玩家名**换成**武将名**
（用户的原始要求：「要详细写哪个武将的具体操作，不能只用座位号表示」）。
它同时打坏了两样东西：

1. `tests/browser.board.mjs` §7 的**断言过期**：它拿 `view.players[].name` 比对弹窗正文。
2. `js/ui/board.js` 的 `_maybeModalFromLog` —— 它拿 `p.name` 去 `line.includes(...)` 认人，
   日志改叫武将名后**永远匹配空** → 弹窗里的名字芯片（`.modal-names`）变空串，**用户看得见**。

根因不是谁写错了，而是**"某段文字是谁产的"没被写下来**：中央弹窗的【观星】正文是
**引擎日志原文**（`board.js` 的 `POPUP_LOGS` / `_maybeModalFromLog` 兜底路径），
而 `_popupOf` 里同样一句观星文案是**界面自己拼的**（`_name(view.turn)`，事件分支）。
**两条路径产的文字长得一模一样、来源不同** —— 引擎一改文案，界面拿玩家名去匹配就空。

**被否掉的选项**：

- **"界面里兜底两种称呼都试一遍就完了"** —— 治了症状：下次引擎改的是**牌的叫法**
  或者**身份的叫法**，界面照样空。根因是"来源没写明"，不是"少写了一个 `if`"。
- **"让引擎回退成玩家名，界面就不受影响"** —— 直接把用户的要求撤了。
- **"界面把日志文本整段解析成结构化数据再渲染"** —— 量级远超收益；
  日志是给人读的，改名只是同一个称呼在两条路径上要保持一致。

**回归防线**：`js/ui/board.js` 的 `_whoOf(pid)` 与 `_maybeModalFromLog`（两种称呼都认、
芯片优先武将名）；`tests/browser.board.mjs` §7（断言正文含**武将名**、⛔ 不含玩家名，
并按剥 `【…】` 段的口径匹配，防「诸葛连弩」里的「弩」假红）。
出处：T22 的实现者定位到行（`board.js:275–290`、`:763–790`；`browser.board.mjs:1025`）；
用户原话见《三国杀 Lite》这一轮的第 2 条 UI 调整。

## D24 把引擎内部字段搬进**共享文字**之前，先问「它此刻是不是已经公开」

**决定**：任何要写进**所有人共享的文字**（日志、待决提示、事件 label、结算面板）的
引擎字段，落地前必须先核**这个字段此刻的可见性**。本作的硬例：
`p.general` 在**选将中途**就有值（每人点了武将就赋值），而 `p.generalRevealed`
要到**选将结束**才置 `true`（`engine.js:53` 初始 `false`，`phases.js` 的 `stepAfterDraft` 才置真）。
所以武将名必须经 `who()`（里面加 `generalRevealed` 闸，没亮 → 回退玩家名，见 `generals.js:233`）。

**为什么**：T22 若照字面"日志里写 `p.general` 的武将名"，**选将阶段任何一条日志都会把
还没亮的武将牌提前广播给所有人** —— 这是铁律 2（隐藏信息不许进任何报文）事故。
而它看起来只是"改个显示文案"，很容易被当成零风险改动。

同类字段以后还会有：`identity` / `identityRevealed`、手牌、牌堆顺序。
**一句自查**：这个字段现在**别的玩家能不能看见**？看不见，就先把闸补上再写文字。

**被否掉的选项**：

- **"日志里先不写武将名，等选将结束再写"** —— 选将阶段的日志就变成玩家名，
  用户看到的仍然是「甲1」，等于没改。
- **"选将阶段干脆不打日志"** —— 用户的诉求是"看得出谁在干什么"，静音是反方向。
- **"把 `generalRevealed` 提前置真"** —— 直接泄露武将牌，比不写更糟。

**回归防线**：`tests/rules.test.mjs` 钉 `who({generalRevealed:false}) === '甲1'`；
牙齿证明 —— 把 `who()` 换回 `p.name` 这条变红，恢复即绿。
出处：T22 的实现者发现（`generalRevealed` 的赋值点在 `phases.js` 的 `stepAfterDraft`）；
铁律 2 见工作区 `AGENTS.md` 的「架构铁律」。

## D25 几何量对了 ≠ 能用：命中测试必须单列一条

**决定**：凡是"新加的可点元素"（按钮、头像、手牌、技能键），验收**必须同时**有两条，
两条都过才算"能点"：

1. **几何**：`getBoundingClientRect()` 在它该在的框内，且没有被任何祖先 `overflow` 裁掉；
2. **命中**：`document.elementFromPoint(中心)` 命中的**就是它自己**，并且**真鼠标点一下
   真的有反应**（不是程序化 `.click()`）。

只量几何不够，只做程序化点击也不够。

**为什么**：T19 新增的「整理手牌」按钮，`rect` **完全正确**（在框内、44×44、不被裁），
但**真鼠标点不动** —— `.hand-strip` 上的 `transform` 给自己开了**层叠上下文**，
按钮的 `z-index:10` **只在条内有效**，于是整块被 `.board-me`（`z-index:4`）盖住。
程序化 `.click()` 绕过了命中测试，所以一直是"绿"的；`elementFromPoint` 一打就露馅。
改成 `z-index:5` 之后，真 CDP 点击 `aria-pressed false → true`。

同理 T23 的另一半：三个技能键 **`rect` 全对却行高 0px**（被 `.me-skills` 切掉）——
"元素在框内"与"它还能显示出来"是两件事。

**被否掉的选项**：

- **只量 rect** —— 就是这次踩的坑：不可见的元素 rect 照样规规矩矩。
- **只靠 `elementFromPoint`** —— 它只回答"最上面的是谁"，回答不了"是不是被切掉一半"；
  被 `overflow:hidden` 裁掉的元素有时仍能被命中测试返回（命中区域落在父元素上）。
- **只靠尺寸体检（44px）** —— 它量**尺寸**，不管遮挡、不管裁切、不管谁能盖住谁。
- **用程序化 `.click()` 当"点得动"的证据** —— 它**跳过命中测试**，是假绿的主要来源。

**回归防线**：`games/sanguosha-lite/tests/browser.board.mjs` 的点击组
（`elementFromPoint` 命中 + 真鼠标点击后看状态变化，如 `aria-pressed`）；
`tests/browser.e2e.mjs` 的"锁输入"组用的也是**真鼠标**（不是 `.click()`）。
出处：T19 的「整理手牌」按钮与技能键；T23 的 ui-dev 用 `elementFromPoint` 量出来后修掉；
本条由这一轮的第 ⑤ 条测量要求（"打它中心命中的是不是它自己"）发现。

## D26 状态在宿主重挂时丢失：记录必须发生在丢失之前

**决定**：凡是"要跨平台重画保住"的状态（滚动位置、光标、展开状态、输入中的文本），
**记录动作必须挂在"丢失之前"的事件上**（如元素自己的 `scroll` / `input` 事件），
⛔ **不许在 `render()` 开头"顺便读一下再存"**。

**为什么**：平台的每帧顺序是

```
UI.clear(panel)    ← 摘节点 ⇒ 浏览器立刻把 scrollTop/scrollLeft 复位 0
host.append(root)  ← 同一个节点挂回去（节点没换）
board.render()     ← 这里才轮到游戏代码
```

所以到 `render()` 里再读，**永远是 0** —— "记录"分支拿到的是已经被清零的值，记忆表恒空，
恢复分支自然从不执行。T24 就是照着"在 render 里记录 + 恢复"写的，于是**只修了恢复、没修记录**，
联机壳里必红。修法只有一行：把记录搬到 `.rec-list` / `.stage-mates` 的 `scroll` 事件里
（`{passive:true}`），恢复仍留在 `_keepScroll()`。

**关键推论**：**"单机能过、联机不过"往往不是探针的错，是宿主的差别** ——
单机局不摘节点（`replaceChildren` 内部换子树），联机壳每帧 `UI.clear(panel)` **摘整个节点**。
同一个 `_keepScroll()` 在两种宿主下结论相反。

**被否掉的选项**：

- **"在 `render()` 开头读、读不到就用上次的值"** —— 就是这次的错：读到的永远是 0，
  而 0 是合法值，无法区分"用户真的置顶了"与"平台刚清零"。
- **"用 `MutationObserver` 监听节点被摘"** —— 摘节点不是标准的"变更回调时机"，
  而且平台每帧都在摘，成本与复杂度都不划算。
- **"让平台别摘节点"** —— 动的是平台共用层（会影响另外三个游戏），
  为游戏里一个滚动条去改平台，代价与风险都不成比例。

**回归防线**：`tests/browser.e2e.mjs` 的验收 ⑥ 三步反面对照 ——
① 用户主动点开 → `scrollTop == 0`；② 滚到底 → **连着重画两次** → 恢复到夹过的值（容差 2px）；
③ 关掉**再点开** → 必须回到 0（防"修好恢复、弄坏置顶"）。
外加"只滚一下、之后 1.2 秒不碰任何东西，位置不许变"（自然推帧漂移探针）。
出处：T24 的实现者写了 `_keepScroll()`；**根因由 T9 的实现者用"节点身份探针 + 读源码"钉死**
（探针直接回答"同一节点被重置"还是"节点被换掉"，这一步排除了"探针坐标系错了"的嫌疑）。

**补记（T28 收尾，已修好并量到证据）**：最终修法是三件小事合起来 ——

1. **记忆挂在元素上**：模块级 `WeakMap<Element, number>`（`board.js` 的 `SCROLL_MEM`），
   两个 `scroll` 监听写元素；`_keepScroll()` **优先读元素**（实例上的 `_scrollMem` 只留兼容镜像）。
   **理由**：元素活着，实例可能换。
2. **恢复加 `rAF` 兜底**：`if (!el.isConnected) requestAnimationFrame(apply)`
   —— 抄刀马 `_pinLog()`（`games/blade-steed/js/ui/board.js:449`）。根元素还没插进文档时
   写 `scrollTop` 等于没写（没有布局盒）。
3. **`_openRec()` 同时清掉元素记忆**：否则"用户点开置顶"会被恢复旧值破坏。

**实测证据（这次是强证据，不是"等 1.2 秒不变"）**：

```
程序化设值派 scroll 事件 1 次；真鼠标滚轮（CDP mouseWheel）后事件累计 2 次、位置 547
强制重画：render 调用 2 次｜摘下后 0 → 第一次重画 547 → 第二次 547 → 等一帧 547（期望 547）
关掉再点开 0
```

⇒ 「事件不派」这个分支**没被触发** ⇒ 「挂 scroll 事件」这条路仍然成立，
**不需要**改成"每帧主动读一次暂存"。

**顺带量到的平台事实（第二条保住"记录必须发生在丢失之前"的证据）**：
`FrpRoom.render()` 的重画指纹里含**整份 view**（`shared/ui/room.js` 的 `JSON.stringify(r.view)`）
⇒ **几乎每一次 view 变化都会挂牌桌** ⇒ 用户往下翻记录时**几乎每次更新都会被弹回顶部**。
这条把 ⑥ 从"稀有瑕疵"改判成"高频该修"，也让"等 1.2 秒位置不变"这条证据彻底作废
（那 1.2 秒里可能一帧都没来，只能写成「未重挂时位置稳定」）。

**补记二（T30 结案，真修好了）**：最终三处一起改 ——

- **A** `render()` **末尾**（`_scheduleReconcile()` 之后）再 `_keepScroll()` 一次；
  **开头那次保留**（兜底"整帧没有 paint"的路径）。
- **B1** `_paintRec()` 加 `rkey`（条数 + 每条原文）短路 —— 弹窗开着时**内容没变就不再
  `replaceChildren()`**（正是它每帧把 `scrollTop` 复位 0）。
- **B2** `_paintMates()` 的「这一帧没有队友手牌」分支加 `keepLeft` —— F1 当初只修了
  "真重建"那一支，**这是另一半**。

**证据：一整帧四个采样点**（2 / 46 / 171 / 405ms）全是 547，差 0px。
**红线自查**：往日志加一条 ⇒ 行数 55 → 56（断言 `n1 === n0+1`）⇒ 内容真变了照常重画，
**短路没有吞新日志**。（⚠️ 对账路径会再贴一次最新视图，行数**合法地**停在 56 ——
所以"内容变回去也要 +1"这条断言被**自己判为过严并降级成打印**，不是放宽既有断言。）

**这一轮最值钱的教训（写给以后判时序类缺陷的人）**：

> 前两轮 ⑥ 都被判成「**记忆根本没写进去**」，而真相是「写了、但同一帧后面被 paint 清掉」。
> 原因只有一个：**证据只取了某一时刻**。
> ⇒ **时序类缺陷的证据必须覆盖一整帧（多点采样）**，否则「没记录」与「记录后被清」
> 在单点采样下**无法区分**，会被一直误判到修错方向（去改记录逻辑）。

这条与前头"记录必须发生在丢失之前"是一对：**先保证丢之前有记，再保证记之后没人清。**

## D27 「覆盖不全」≠「量错」：绿的和该绿的，是两件事

**决定**：任何"全部通过"的结论，必须同时说明**它覆盖了哪些档**。凡是靠"这一档绿了"去
推断"那一档也没问题"，一律算**未验**。作断言时，**宁可用确定性夹具钉住最坏档，
也不要靠"随机抽到"来覆盖**。

**为什么**：这一轮同一条链上，**同一个缺陷被"覆盖不全"漏过去三次**：

1. `browser.size.mjs` 量的是牌桌 / 座位 / 手牌区 / 操作区 **四个区块** ——
   **技能行不在其中** ⇒ 技能键被裁 26 / 26 / 73px，一直没人量到（尺子没坏，是没量到那儿）。
2. 补上技能行之后，夹具里两个客户端**都只有 2 个技能键** ⇒ 单排、`client == scroll`、
   天然绿。而**3 个技能键就已经换第二排**（孙权实测 5px）、4 个更糟（刘禅 22.8px）。
3. 同一条链上还漏着**"武将区压到邻居座位的体力/装备"** —— 这在 8 人身份局里等于
   **看不见对手还有多少血**，而 §16 当时只覆盖 3 座斗地主。

三次都不是"尺子不准"，而是"没量到该量的地方"。**量错的修法是修尺子；覆盖不全的修法是补范围。**
两者混起来，就会得出"工具在撒谎"或"其实没问题"两种错误结论。

**推论（已经踩过的坑）**：靠"选将时优先挑技能最多的武将"来覆盖最坏档**不可靠** ——
3 选 1 里四技能武将只占 6%，同一套用例会时红时绿（实测三跑：绿 / 红 5px / 绿）。
⇒ 最坏档必须用**确定性夹具**（固定武将 + 固定格局）钉住，并且断言"本档必须真的进到这个形状"
（例：技能行高度 `fh >= 88`，只出现一排就判红）—— 否则"没测到"会伪装成"测过了"。

**另一条配套纪律（两个套件互相声明盲区）**：`browser.e2e.mjs` 只判"元素是否跑出牌桌 / 被
`overflow:hidden` 祖先裁掉"，它**测不出**"区与区互相压住"；`browser.board.mjs` 负责区与区相交。
**一方的绿不替另一方背书**，报告里必须写"这一条不在我的判据内"。

**被否掉的选项**：

- **"多跑几次总能撞到最坏武将"** —— 概率不可控，且失败时无法区分"真缺陷"与"没抽到"。
- **"把容差放宽一点就绿了"** —— 22.8px 的裁切不是容差问题。
- **"用视口宽度猜该不该进矮牌桌分支"** —— 牌桌高度由平台外壳决定，与视口宽度不是一一对应；
  必须**量牌桌实际高度**（本作用 `_markShortBoard()` 量 `.board-me` 的 `scrollHeight > clientHeight`）。

**回归防线**：`tests/browser.board.mjs` §17（`mode8` + 固定长名四技能武将，四档
`client == scroll`，并断言"本档技能行必须 >=88 高"）；区与区相交基线（武将区∩操作区
1154.9 / 1051.1 / 55.9 / 70.4px²，**只许减不许增**）；邻居座位可见件 0 处被压。

## D30 上游有六个文件被打了补丁（子路径 / 联机地址 / 载入超时 / 中继容错 / 退出兜底），更新脚本负责重打

| 文件 | 改了什么 | 不改会怎样 |
| --- | --- | --- |
| `apps/core/noname/init/import.ts` | `/card/…` `/character/…` `/mode/…` `/extension/…` 改成相对文档 | 根绝对路径绕过 `/noname/` 前缀 ⇒ 404 或**同一模块两份实例** |
| `apps/core/scripts/vite-plugin-importmap.ts` | import map 的地址、入口脚本 `src`、`/jit-test.ts` 探针改成相对地址 | `lib`/`game` 各两份 ⇒ `lib.config.characters` 是 undefined ⇒ **白屏** |

| `apps/core/noname/init/index.ts` | 载入超时兜底 10 秒 → 30 秒 | 手机/隧道慢一点就弹「游戏似乎未正常载入」误报（见 D32） |
| `packages/server/src/server/createServer.ts` | 每条连接 + WebSocketServer 挂 `error` 监听；`host` 只绑回环 | 一个非法帧让 `ws` 抛未处理异常，**整个进程崩**（见 D31）；绑 `0.0.0.0` 会在局域网多开一个口 |
| `apps/core/noname/init/browser.js` | `game.exit()` 关不掉窗口时**回主菜单** | 悬浮球里的「退出」按了没反应（浏览器只允许关掉脚本自己开的窗口） |

**为什么必须改**：浏览器按 **URL** 区分模块。index.html 用 `./noname.js`
（= `/noname/noname.js`），而 import map 把 specifier `noname` 指向 `/noname.js`（= 站根的
另一份文件）。两份 `lib` / `game` 同时存在时，先跑的那份初始化了配置、后加载的武将包读到的是
**另一份空的** —— 于是 `TypeError: Cannot read properties of undefined (reading 'characters')`，

**代价**：更新上游之后补丁要重打。`node tools/noname-update.mjs` 把"下载 → 覆盖 → 打补丁 →
`pnpm install` → `pnpm build`"合成一条；**锚点找不到时它会让整个更新失败**，
而不是悄悄产出一个坏 dist。

**被否掉的选项**：**服务端把根绝对路径 302 到 `/noname/`** —— 也能统一模块身份、且不碰上游，
但每个模块多一次往返（首屏 ~250 个模块），且"哪些路径要转、哪些不要"会变成一堆特例；
不如改上游那 6 行干净。

**回归防线**：`tools/check-noname.mjs` 里 "所有模块必须都从 `/noname/` 加载" 与

## D31 联机中继：**同进程 + 裸 TCP 转发**，不另开端口、不改上游中继

**决定**：用户要"我和同学远程联机，网页打开就能打"。无名杀的联机是
"客户端 ↔ 中继 ↔ 客户端"（规则在房主浏览器里，中继只登记房间、转发报文），
所以必须有一台中继。做法：

1. 在本进程里 `import('games/noname-web/packages/server/dist/index.js')` 起上游的
   `createServer({port: 8231})`，**只监听 127.0.0.1**；
2. `server/ws.mjs` 增加 `proxy` 选项：收到 `Upgrade: /noname-online` 时
   `net.connect(8231)`，把客户端握手请求**逐字重放**过去，然后双向搬字节 ——
   **不解析 WS 帧**；
3. 打补丁把无名杀的 `lib.hallURL` 改成"按当前页面现算"（`wss://<当前域名>/noname-online`），
   于是「联机」里地址**已经填好**。

**为什么不用独立进程 / 不新开隧道**：

| 选项 | 为什么不选 |
| --- | --- |
| 另起一个 node 进程跑中继 | `stop.cmd` 只 kill 主 PID（Windows 没有信号），中继会**变成孤儿**；还得给它加心跳、日志、重启策略 |
| 请用户去面板加一条 8082 隧道 | 违反"不要动隧道"的约定，也把"网页打开就玩"变成两步；多一条隧道就多一处会坏的地方 |
| 让客户端直连中继（P2P/WebRTC） | 上游没有这条路径（D1 已删过这类代码），而且要 STUN/TURN，代价高一个量级 |
| 解析并代理 WS 帧 | 中继协议是上游的私货（`["server",…]` 数组），解析就等于把上游的协议抄进我们仓库，它一改我们就坏 |

**代价 / 已知风险**：

- 中继和平台**同进程**：第三方代码（`ws` 包）的未处理异常能带走整个平台。
  ⇒ 打了补丁给每条连接挂 `error` 监听（上游没有；一个 close 帧里写 status code 0
  就能让上游中继崩掉，体检里真踩到了）。中继起不来（没构建 / 8082 被占）**不影响单机玩**，
  启动日志会警告，`/noname-online` 返回 502。
- 中继状态全在内存里：进程一重启，**房间列表清空**（牌局本来也在房主浏览器里，
  双方刷新重开即可）。

**回归防线**：`tools/check-noname.mjs` 的「联机中继」一节 —— 从 **7891 的 `/noname-online`**
握手、拿到 `roomlist`、报身份后收到在线列表；三条缺一条就变红。

## D32 首屏：gzip + 10 分钟缓存；手机：**外壳 iframe** 做伪横屏

**决定**（两件相关的事，都是为了"手机能真的玩起来"）：

1. **gzip + ETag + `/noname/` 下 `max-age=600`**（`server/http.mjs`）。
   实测首屏 250 个请求：**压前 3.48 MB → 传输 0.80 MB**。
   Range（音频边播边取）**不压** —— 字节范围是压缩前的坐标；几 KB 的小壳文件也不压。
   压缩结果按 `路径+大小+mtime` **缓存在内存**里（上限 32 MB，LRU），`dist` 一换自动重压。
2. **伪横屏用外壳 iframe**（`web/noname-frame.html`，路由 `/play/noname`）。

**为什么要 gzip**：用户报"手机进不去，显示「游戏似乎未正常载入，是否重置游戏」"。
查下去那是上游的**载入超时兜底**（`setTimeout(lib.init.reset, 10 秒)`），
不是游戏坏了 —— 手机 + 隧道拿 250 个模块超过 10 秒就会弹。压缩把首屏砍到 0.8 MB，
再从补丁把兜底放宽到 30 秒。

**为什么伪横屏用 iframe**：无名杀的排版按**视口尺寸现算**。给整页加 `rotate(90deg)`
只是把"竖版排版"歪着放。放进一个**横向 iframe**（844×390）里，它的排版/缩放/触摸坐标
本来就按横屏算，外壳只负责把这块画面转 90° 摆满竖屏。判据只用 `(pointer: coarse)`
（⛔ 不能用 `navigator.maxTouchPoints`：触摸屏 Windows 笔记本是 10，会把自己当手机）。

**被否掉的选项**：

- **手改上游布局代码做横屏** —— 那是在重写无名杀的 UI，违背 D28「整包托管」；
- **只调 `max-age` 不压** —— 首屏照样要传 3.5 MB，第一次进还是十几秒；
- **给 JS 上 `immutable` 长缓存** —— 动态 import 的 URL 没有 hash，`dist` 更新后
  新旧模块混着跑 = 白屏（就是 D30 那个坑的另一种触发方式）。

**回归防线**：`check-noname.mjs` 里 gzip/304/Range 三条、外壳 390×844 必须量到
"内容 844×390 且转了 90°"、电脑必须跳回 `/noname/`、首屏传输量必须 < 压前的 60%。

## D33 账号升级与无名杀绑定：登录门 + **注入桥接**，不改 `dist`

**决定**（四件事，同一个目标：把无名杀从"另一个网站"变成"平台的一个游戏"，但不动上游产物）：

   （否则 250 个模块每个都要过一遍登录逻辑，还会把 SW 打乱）。
3. **身份绑定用注入脚本，不改 `dist`**：`server/http.mjs` 在 `index.html` 的 `</head>` 前插入

   「邀请平台好友」；上报"我在哪个房 / 开没开局 / 允不允许观战"。
4. **好友在线状态与邀请**：`server/noname-presence.mjs` 存内存态（心跳 15 秒、TTL 45 秒），
   `hub.refreshFriends()` 把 `playing:{game:'noname',code,started,observe,joinable}` 并进好友列表；
   `INVITE_REPLY` 遇到 `game:'noname'` **只转发回执、绝不进平台房间层**（房号格式完全不同）。

**为什么必须"注入"而不是改 `dist`**：

- `dist/` 是 `pnpm build` 的产物、1.3 GB，用户机器上重建一次要几分钟且会短暂白屏；
- 上游一更新，改过的产物全丢；注入脚本是服务端行为，重建多少次都还在；
- 桥接只碰**公开的运行时接口**（`lib.config` / `game.saveConfig` / DOM），
  上游内部改结构时最坏是"桥接失效、游戏照常"，不是白屏。

**被否掉的选项**：

- **改 `dist` 里的 index.html / 打包进 bridge**：见上，重建与上游更新都受不了。
- **把平台登录塞进无名杀自己的登录框**：那是改造原版（违背 D28），而且会跟它自己的
  `localStorage` 账号打架。
- **让无名杀房间走平台房间层**：房号/协议/成员模型完全不同（它自己的中继是内存态，
  一局的状态在房主浏览器里），硬接等于重写上游联机。
- **头像只存 base64 进 SQLite**：数据库会迅速膨胀、每次拉好友都传图；落盘 + URL 更省。

**代价（记住）**：

- 联机邀请只发给**平台 WebSocket 在线**的好友；只在无名杀页面里活着的人收不到弹窗，
  他们的入口是"好友列表里显示正在玩 → 点加入"。这是刻意的，不是漏做。
- 无名杀侧的上报是内存态：进程重启就清空（好友最多看到 45 秒的"正在玩"残影）。
- 已开局且房主没开「允许观战」的房间，好友点进去会被无名杀自己拒绝：
  桥接把 `alert("请稍后再试")` 换成一句人话（"这局已经开始了，房主没开观战"）。

**回归防线**：`npm test` 的「无名杀接入」「头像」两节（401 / 邀请 / 回执不建房 / 上传与默认 SVG /
伪装图片被拒）+ `node tools/check-noname.mjs`（登录门、注入脚本、昵称头像、邀请入口、
真浏览器 390×844）。

## D45 音频 URL 去扩展名，防 IDM / 迅雷自动抓取（2026-11）

**现象**：用户打开麻将，IDM 把 `/mahjong/audio/*.mp3|ogg|wav` 全部抓进 `E:\下载`，
一次访问几十个文件、反复访问累计 2000+ 个。下载器把 URL 里的媒体扩展名当成"可下载资源"。

**决定**：

- `shared/ui/no-idm.js`：拦截同源、路径以 `.mp3/.ogg/.wav/.m4a/.aac/.flac` 结尾的
  `fetch`、`XMLHttpRequest.open`、`new Audio()`、`HTMLMediaElement.src`、`setAttribute('src')`，
  把扩展名去掉再请求。只动音频，图片/脚本/页面不碰。
- `server/http.mjs` 的 `candidatesFor()`：最后一段没有点的路径，按
  `.mp3 → .ogg → .wav → .m4a → .aac → .flac` 探测真实文件；`sendFile()` 按真实扩展名
  发 `audio/*`，并加 `Content-Disposition: inline`。老地址（带 `.mp3`）仍然 200。
- 入口页统一引入该脚本：平台游戏/首页直接写 `<script defer>`；无名杀/狼人杀/麻将/大富翁
  由 `server/http.mjs` 注入。**以后的新游戏也要接这一行**。

**为什么不用别的办法**：

- **改 IDM 设置**：只能解决用户自己这台机器，访客的下载器管不了。
- **`Content-Disposition: inline` 单独用**：扩展名还在，IDM 照样认。
- **把音频塞进 Blob/Service Worker**：`<audio>` 直接播放的路径仍会暴露媒体 URL，
  改造面大、还要动上游代码；去扩展名最小且对上游透明。
- **只在麻将里改文件名**：以后每个游戏都要改一遍；平台层注入一次，所有游戏生效。

**代价**：URL 不再"看起来像文件"，对调试略不直观；`<audio>` 请求返回的 MIME 仍是
`audio/*`（为了能播），所以理论上仍可能被按 MIME 嗅探的下载器抓 —— 实测 IDM 主要按扩展名，
用户复验后如仍有弹窗再考虑把 fetch 响应改成 octet-stream + 客户端重包 MIME（更复杂）。

**测试**：`tests/mahjong.test.mjs`（无扩展名 200 / MIME / inline / 老地址 200 / 不存在 404）、
`tests/browser.smoke.mjs`（`FrpNoIdm.fix()` 去扩展名、`new Audio()` 的 src 已去扩展名）。

- **赛道用上游已有的路线**：优先 `coast`（沿海闭环），否则 `ring`，否则最长路线；

**被否掉的选项**：

- **服务器权威车辆物理**：要让服务器跑 cannon + 8 台车的悬挂/轮胎，还要把状态回传给客户端；

## D47 地平线手机 HUD：六组整体编辑 + CSS 变量（2026-11）

**用户要求**：小地图缩到左上、仪表盘缩到它下面、左右按键放大并向内/上挪、升/降挡别挡技能点，
并在游戏主菜单加「手机界面布局」让用户自定义各 UI 的位置/大小、可重置。

**决定**：

- **六组整体**：小地图、仪表盘（表盘+挡位+速度+RPM）、技能点、左转向、右油门、顶部小按钮。
  每组一个拖动框 + 大小滑杆 + 显隐；不做每颗按钮独立，避免手机上点错和设置页爆炸。
- **只写 CSS 变量**：`--hud-<组>-x/y/s`；游戏绘制、物理、网络完全不知道布局存在。

- **联机计时条不另设第七组**：手机上收成小地图右边的一条（用时+名次），
  由 JS 在 `applyLayout` / 开始驾驶时按小地图实际位置重算，地图拖动/缩放后跟着走。
- **每次改动自动保存**；「恢复默认」一键还原。编辑器可收起面板，避免挡住底部按键。

**被否掉的选项**：

- **每颗按钮/每个 HUD 数字单独编辑**：最灵活，但六组已经覆盖用户实际痛点；再拆会让

- **自由画布 + 任意旋转**：维护和回归成本高，且会让布局跑到屏幕外；只用平移/等比缩放。
- **布局上传服务器/跟账号走**：手机和平板尺寸不同，一份布局反而更差；没有跨设备需求。
- **桌面也改成新布局**：用户只要求手机；桌面保留上游右下角表盘，避免影响大屏体验。

**代价 / 已知限制**：

- 每组只能整体移动/缩放，不能单独挪"挡位"和"速度"两个数字。
- 布局以像素平移保存，不按屏幕比例重算；换到尺寸差很多的设备可能要微调。
- 编辑面板在顶部，很小的横屏（宽 < 568）仍可能压住顶部小按钮；面板可收起，或用四向微调。

## D48 AI 小镇：上游世界进程原样跑，平台只包一层

**决定**：`github.com/mewamew/my_ai_town` **整份复制**进 `games/ai-town/upstream/`（不是 fork），
Rust 的 `town-manager` / `town-host` 编译成两个 exe；Node 平台只做五件事：

1. **按平台账号拉起 manager**：`data/ai-town/users/<平台用户ID>` 为 `--root`，
   一个用户一个 manager，最多同时 2 个（用户明确要 2 个房间）。
2. **房间表**：平台自己发 6 位房间号，记房主/镇/成员；邀请和深链都走平台，
   不把上游随机端口和 `?session=` 交给浏览器。
3. **账号注入**：页面由 `http.mjs` 注入 `window.__FRP_ME__`，桥脚本显示平台头像/昵称；
   化身默认名字用平台昵称。WS 反代还会把 `frp_user / frp_name / frp_role / frp_room / frp_avatar`
   注入上游握手，host 据此认人。
4. **存档**：上游 host 自己写 `world.json`；房主退出 = 保存并关镇；客人不落盘。
5. **布局**：手机只留背包键；位置/大小按平台账号存 `user_layouts`，坐标/尺寸服务端夹值。
   旧账号的四键布局数据保持原格式，只应用/调整背包（2026-11 用户拍板：手机直接点地图，
   不需要摇杆/互动/换目标）。

**联机化身（2026-10 用户拍板：改 Rust 内核，不做只看）**：

- kernel 现在认识多个“玩家控制的化身 actor”：房主仍是 `player_avatar`，访客是
  `guest:<平台用户ID>`（稳定、从平台身份生成，不写进存档）。
- host 给每个访客一条独立控制租约 + 独立方向输入；处理某个访客报文时临时把
  `world.active_actor` 切到它的 actor，复用原来的命令事务与 epoch 回执，处理完切回。
- 访客只能发只读公开查询 + 自己的 `Avatar / AvatarInput`；`Possess` 与世界设置
  （开始/暂停、天气、速度、请村民等）一律拒绝，错误文案写明由房主管理。
- 访客头顶显示**平台头像（22px 圆点）+ 平台昵称**：名册新增可选 `avatar_url`，
  由 host 按握手身份填；前端 `town-2d` 画在名字上方，不占屏幕。
- 客人离开/断线时 actor 留在内存但下场，`snapshot()` 过滤所有 guest actor 与访客互动；
  保存后的 `world.json` 只有房主，重开不会出现 `guest:` 校验失败。
- 访客是临时的：同一访客重进会复用这个 actor 的 last locus（如果还在同一 host 生命周期内）。

**内置小模型**：

- **只在服务器跑**。`llama-server.exe` 用 Vulkan（优先 RTX 5060 独显），
  host 按需拉起、随世界退出；手机只收画面和对话结果。
- 模型文件共享一份 `data/ai-town/models/model.gguf`，每个用户目录用**硬链接**，
  避免 2 个房间各复制一份 505MB。
- 推理程序随仓库（`upstream/builtin-model/`），模型不进 git、换机器下载一次。

**被否掉的选项**：

- **把世界逻辑搬到浏览器/WASM**：上游是 Rust 服务端内核 + 多进程，搬过去等于重写；
  手机也扛不住模型。
- **每个客人开一个 host**：不是同一个世界，朋友看不到彼此，失去联机意义。
- **直接把上游 endpoint 给浏览器**：会暴露 `127.0.0.1:随机端口` 和 `session`，
  也没法统一登录/邀请；必须由平台反代。
- **多人同时降临一次做完**：要改内核的“单 `player_avatar` + 单控制租约”模型。
  2026-10 用户明确要求“现在就改内核，做完整多人化身”，所以**没有**停在“客人只看”
  的折中方案；实际改动见上面「联机化身」。
- **每个访客一个浏览器/一个世界**：不是同一个小镇，失去联机意义。
- **手机端跑小模型**：用户明确担心手机带不动；服务器推理是唯一稳妥方案。

**代价 / 已知限制**：

- 每个开镇用户一个 manager/host，两个房间就是两个进程；内存和显存按房间叠加。
- 世界设置只归房主；访客点「开始/暂停」或改天气会被服务端拒绝，手机桥也隐藏了这两个按钮。
- 访客不存档：客人可以进房主的小镇一起玩，但这次访客的身份/位置不会写进房主 `world.json`；
  想保存自己的镇就自己开一个（用户已确认“房主存档、客人临时”）。
- 新镇默认给一份世界观（否则化身命令全被拦），玩家可在设定里改。
- 模型下载/更新仍走上游的清单与校验；离线机器要提前放好 `model.gguf`。


## D49 狼人杀：所有选人动作都能"不选"，夜里死的人先留遗言，白痴翻牌即免死（2026-10）

**决定**（用户逐条拍板，原话"凡是行动都加"）：

1. **空选**：放逐投票、警长投票、守卫、狼人（撤票＝空刀）、狼美人、预言家、猎人都允许"这一轮不选"。
   服务端一律收显式 `seat: null`；派发到各角色分支时**必须先判 `null`**，
   ⛔ 不能写 `const target = Number(body.seat)` —— `Number(null) === 0` 会把"不选"变成"查 0 号位/刀 0 号位"。
   "不选"的效果按牌面算：空守会**清掉连守记录**（否则"不能连守同一个人"会跨空守生效），
   空刀会**从 `wolfVotes` 里删掉自己那一票**（狼队按多数决，撤票要能改变结果），空验不留结果。
2. **夜里死的人有遗言**：天亮 → 播报死讯 → `DAY_LAST_WORDS` → 猎人开枪/移交警徽 → 白天讨论。
   之前的实现只在"白天被投出"时给遗言，夜死的人一句话说不了。
3. **白痴翻牌后再被投出不死**：翻牌是"所有人都知道他翻过"的公开状态，第二次被投出只播报"本轮放逐无效"；
   而"没翻过的白痴"被投出才翻牌。注意 `goodSkillsDisabled`（长老被狼刀）只该禁**技能**，不该禁这个。
4. **发言可以连发多段**：引擎里 `speech` 本来就不换人，是**输入框按 Esc 会结束发言**把想多说几句的人一击交了麦。
   Esc 现在只关 @ 候选；180 秒是整轮发言的总时长，**不因为发了一段就重置**。

**为什么白痴的免疫要做在服务端、而不是前端算**：前端拿不到别人的 `role`（`viewFor` 只给公开身份，
未知角色被兜成 `Villager`），"谁是翻牌白痴"根本算不出来 —— 所以公开视图加了 `idiotRevealed` 布尔位，
投票进度/结果都按它排除免疫者。

**被否掉的选项**：

- **让"不选"等于"没行动"、什么都不做**：守卫那条会让"隔一晚才能再守同一个人"的检查读上一夜的记录，
  出现"我明明空守了却还是不能守他"；必须显式清。
- **夜里死者不给遗言**（保持旧行为）：用户明确要"夜里死也要留遗言"。
- **白痴翻牌后仍然死**：用户明确要"翻牌后再投出不死"。
- **把发言做成一次性提交**（提交后换人）：用户要的是"一轮里想发几段发几段"。

## D50 狼队夜间频道不等于"做聊天"（2026-10 用户要求）

**决定**：`NIGHT_WOLF_ACTION` 阶段，**存活狼人**可以互发短消息（`wolfChat`），消息落 `scope:'wolf'`，

## D51 恶夜骑士（恶灵骑士）按网易官方规则：反伤一次性、夜伤永久免疫（2026-10-26 用户拍板）

**背景**：审计里我把"反伤名额被当夜已经死了的人吃掉"当成 bug（原来的 L4），用户拿官方规则答复：
**那不是白吃，官方就是这样**。所以这一条从"待修"改成"已经是对的"，并补用例钉住，防止以后被人"修"坏。

**官方规则（用户转述豆包的原话，作为本项目的口径）**

1. **反伤正常结算**：狼刀女巫、女巫毒恶夜骑士 → 天亮女巫被反伤出局，恶夜骑士没事
   （它永久免疫夜间伤害，毒不死）。
2. **反伤一辈子只触发一次**：这次毒触发完，之后再被预言家查验、再被毒，都不会再有反伤；
   **但"免疫夜间伤害"是永久被动**，夜里依旧刀不死、毒不死，只能白天被投票放逐。
3. **同一晚"预言家验 + 女巫毒"**：先结算预言家的反伤（预言家出局），**女巫不会被反伤**，
   **毒药被吞**（用掉了但没效果），反伤也消耗掉了。
4. **它不能自爆、不能自刀；骑士白天决斗它可以直接把它戳死。**

**代码怎么对上**（`games/werewolf/engine/index.mjs`，改之前先读这几行）

| 规则 | 实现 |
| --- | --- |
| 免疫夜刀 | `nightResolve()` 里 `victim.role === 'EvilKnight'` 直接跳过，不产生死讯 |
| 免疫毒 | 毒药循环里 `victim.role === 'EvilKnight'` → `continue`（毒药照样算用掉 = 被吞） |
| 反伤只触发一次 | `g.evilReflectUsed`，结算时置真，之后永不再进这个分支 |
| 同晚验优先 | `const reflected = seer && seer.alive ? seer : witch && witch.alive ? witch : null;` |
| 天亮才死 | 夜里只记 `g.night.reflectTargetId`，`dayStart()` 才把 `reason:'reflect'` 塞进死讯，播报"因恶夜骑士的反噬死亡" |
| 不能自刀 | 狼刀动作里 `target.seat === me.seat` 且角色是 EvilKnight/WolfBeauty → 拒（"这个角色不能自刀"） |
| 不能自爆 | 自爆只对 `WolfKing`（狼王）开放，`WolfKing` 的 `can.wolfSelfDestruct` 也只有狼王为真 |
| 骑士能戳死 | `knightDuel()` 判 `isWolfRole(target.role)`，恶夜骑士属于狼阵营 → 白天直接出局 |

**"目标当夜已经死了"为什么也算触发**：反伤是"谁碰了它就反谁"，被反的人那一夜可能本来就要死
（比如预言家同时被刀）。技能确实触发了、也消耗了，只是没有"额外多死一个人" —— 官方口径如此。

**被否掉的选项**

- **"反伤必须带走一个人，否则不算触发"**：用户明确说不是这样（反伤一辈子只触发一次）。
- **"反伤可以反复触发"**：同上，一辈子一次。
- **"免疫只在那一次反伤里生效"**：官方是永久被动，夜里永远刀不死/毒不死，只能白天放逐。
- **改这个角色为"好人阵营"**：它是狼阵营（`WOLF_ROLES` 里），开房门槛、胜负判定都按狼算。
